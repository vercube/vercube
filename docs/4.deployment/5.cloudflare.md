A Vercube application runs on Cloudflare Workers as it is: the adapter in `@vercube/serverless/cloudflare` turns it into the module Cloudflare expects and gives your code the bindings of each request.

## Setup

In a new project:

```sh
pnpm create vercube my-api --deploy cloudflare
```

In an existing one:

```sh
vercube add cloudflare
```

Either way you get `wrangler.jsonc`, the `preview` and `deploy` scripts, and three changes to your code. This is the entry afterwards:

```ts [src/index.ts]
import { useContainer } from '@/boot/Container';
import { createApp, provideConfig, type App } from '@vercube/core';
import { toServerlessHandler, type CloudflareHandler } from '@vercube/serverless/cloudflare';
import config from '../vercube.config';

provideConfig(config);

const app: App = await createApp();
app.container.expand(useContainer);

if (import.meta.main) {
  await app.listen();
}

const worker: CloudflareHandler = toServerlessHandler(app);

export default worker;
```

- `provideConfig(config)`: a Worker has no file system, so `createApp()` cannot read `vercube.config.ts` at run time. Importing the file puts it in the bundle, and `provideConfig` hands it to `createApp()`. `.env` files are not read on Cloudflare either: use `vars` in `wrangler.jsonc` and `wrangler secret put`.
- `export default worker`: Cloudflare calls the `fetch` of the module's default export.
- `app.listen()` stays. `vercube dev` needs it, and on Workers it binds nothing.

```jsonc [wrangler.jsonc]
{
  "name": "vercube-api",
  "main": "dist/index.mjs",
  "compatibility_date": "2026-11-01",
  "compatibility_flags": ["nodejs_compat"],
  "assets": { "directory": "./public" },
  "vars": {
    "NODE_ENV": "production"
  }
}
```

`nodejs_compat` is required: the framework uses `node:async_hooks` for the request context and reads `process.env`.

```sh
pnpm dev       # vercube dev, on Node, with reload
pnpm preview   # the built Worker on workerd, at http://localhost:8787
pnpm deploy    # vercube build && wrangler deploy (run `wrangler login` once)
```

## Bindings

KV, R2, D1, Durable Objects, queues, secrets and variables are bindings. On Workers they belong to a request, there is no module-level `env`, so read them where you use them through `CloudflareBindings`:

```jsonc [wrangler.jsonc]
{
  "kv_namespaces": [{ "binding": "CACHE", "id": "<namespace id>" }],
  "vars": { "GREETING": "Hello from a binding" }
}
```

```ts [src/controller/VisitsController.ts]
import { Controller, Get } from '@vercube/core';
import { Inject } from '@vercube/di';
import { CloudflareBindings } from '@vercube/serverless/cloudflare';

interface Env {
  CACHE: KVNamespace;
  GREETING: string;
}

@Controller('/visits')
export class VisitsController {
  @Inject(CloudflareBindings)
  private readonly cloudflare!: CloudflareBindings<Env>;

  @Get('/')
  async count() {
    const visits = Number(await this.cloudflare.env.CACHE.get('visits')) + 1;

    // answered now, written after the response is sent
    this.cloudflare.waitUntil(this.cloudflare.env.CACHE.put('visits', String(visits)));

    return { greeting: this.cloudflare.env.GREETING, visits };
  }
}
```

`CloudflareBindings` is a service like any other, bound in `src/boot/Container.ts` (the recipe adds the line):

```ts [src/boot/Container.ts]
container.bind(CloudflareBindings);
```

`env` and `ctx` throw when read outside a request, for example in a constructor or an `@Init()` method. `active` tells whether a request is being handled.

A service that should work on Node too can keep its storage behind an interface and bind the Cloudflare implementation only in the Worker. `KVNamespace` and the other binding types come from `@cloudflare/workers-types`, or from `wrangler types`.

## Static files

Files in `public/` are uploaded with the Worker (`assets` in `wrangler.jsonc`) and served by Cloudflare's edge before your application is asked. A request for `/logo.png` never reaches a controller, and one for a path with no file does.

## Cloudflare Pages

For a Pages project, put the application behind a catch-all function. Static files of the Pages build are served first, everything else goes to the application:

```ts [functions/[[path]].ts]
import worker from '../dist/index.mjs';

export const onRequest: PagesFunction = (context) => worker.fetch(context.request, context.env, context);
```

or build the function straight from the application with `toPagesFunction(app)` from `@vercube/serverless/cloudflare`. For a new project, a Worker with `assets` does the same with one deploy and is what Cloudflare recommends.

## What is different on Workers

- **No file system.** Configuration is bundled (`provideConfig`), static files are served by Cloudflare, and code that reads files at run time needs another source, such as R2 or KV.
- **Setup runs outside a request.** A Worker may not call `fetch()`, start a timer or generate random values while the module loads. If your `setup` or a plugin does, create the application on the first request instead: `toServerlessHandler(() => createApp())`.
- **No long-lived process.** `@vercube/scheduler` keeps timers in a running process, which a Worker is not: use [Cron Triggers](https://developers.cloudflare.com/workers/configuration/cron-triggers/) and add a `scheduled` handler next to `fetch` (`export default { ...worker, scheduled() { ... } }`). Queue consumers and WebSocket servers that hold a connection open need a platform that keeps a process alive, or Cloudflare Queues and Durable Objects.
- **Work after the response** has to be handed to `waitUntil()`, or the isolate may be stopped before it finishes. The adapter does this for buffered telemetry.
- **Compression is Cloudflare's.** The [`compression`](/docs/core-features/configuration#response-compression) setting is ignored: the edge compresses responses and negotiates the encoding with the client.
- **Limits.** A request gets a bounded amount of CPU time, and the bundle has a size limit that depends on your plan. `wrangler deploy --dry-run` prints the size.

## CI

```yaml [.github/workflows/deploy.yml]
name: Deploy
on:
  push:
    branches: [main]

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v6
      - uses: pnpm/action-setup@v4
      - uses: actions/setup-node@v6
        with:
          node-version: 24
          cache: pnpm
      - run: pnpm install --frozen-lockfile
      - run: pnpm run deploy
        env:
          CLOUDFLARE_API_TOKEN: ${{ secrets.CLOUDFLARE_API_TOKEN }}
          CLOUDFLARE_ACCOUNT_ID: ${{ secrets.CLOUDFLARE_ACCOUNT_ID }}
```

Create the token in the Cloudflare dashboard with the "Edit Cloudflare Workers" template.
