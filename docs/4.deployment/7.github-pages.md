title: GitHub Pages
description: Publish the static part of a Vercube application on GitHub Pages
---

GitHub Pages serves files and runs no code, so a Vercube application cannot run there. What can be published is its static part: the files in `public/`, and the answer of every route that is the same for everybody, rendered to a file at build time.

That fits a documentation site, a demo, or a frontend with a small read-only API. An application that takes requests (a `POST`, a login, a search) needs a target that runs code: [Node](/docs/deployment/node-server), [Cloudflare](/docs/deployment/cloudflare), [AWS Lambda](/docs/deployment/aws-lambda).

## Setup

In a new project:

```sh
pnpm create vercube my-site --deploy github-pages
```

In an existing one:

```sh
vercube add github-pages
```

You get a `build:pages` script, `.github/workflows/pages.yml`, and `dist-static` in `.gitignore`. The application itself is not changed: `vercube dev` and `node dist/index.mjs` work as before.

Then turn Pages on once, under **Settings > Pages > Source: GitHub Actions**. Every push to `main` builds and publishes the site.

## What the build writes

```sh
pnpm run build:pages    # vercube build --target github-pages
```

```ansi
[static] ✔ Wrote 2 routes and 1 public directory to dist-static
  /api/posts -> api/posts (412 B)
  /about -> about/index.html (1840 B)

Not exported:
  POST /api/posts: a POST needs a server
  GET /api/posts/:id: the path has parameters: list the paths to render with --routes
  GET /api/search: the handler reads the request (query-param): list the path with --routes to render it anyway
```

The build starts the application without a port, asks it for each route, and saves the answers:

- Everything in `public/` (and any other directory in `server.static.dirs`) is copied first.
- A `GET` route whose handler takes no argument from the request is rendered: no `@Param`, `@QueryParam`, `@Header`, `@Body`, `@Cookie`, `@Request` or any other parameter decorator. Its answer does not depend on the request, so it can be a file.
- Every other route is listed under "Not exported" with the reason. Nothing is dropped silently.
- `404.html` is added: a copy of `index.html` when there is one, so a single-page application keeps routing on the client for paths GitHub does not know.

The application really starts, with its plugins and its connections, so the build needs whatever the rendered routes need (a database to read the posts from). The scheduler is kept from firing jobs. When the files are written the process exits.

A route with a parameter can still be rendered for the values you name:

```sh
vercube build --target github-pages --routes /api/posts/1,/api/posts/2
```

A path listed in `--routes` that cannot be exported (it answered 404, or collides with another file) fails the build, so a deploy never publishes a site with a page missing.

`--out` changes the directory (`dist-static` by default). It is emptied on every build, so it has to be a directory of its own: the build refuses the project root, `src`, `public`, the build output, and any directory that has files in it which an earlier export did not write.

## Where a route ends up

A JSON route is written at its own path, without an extension, so the frontend calls it the same way against the export and against the server:

```ts
// works on GitHub Pages and under `vercube dev`
const posts = await fetch('/api/posts').then((response) => response.json());
```

GitHub serves a file without an extension as `application/octet-stream`. `response.json()` does not look at the content type, but a client that checks it will not see `application/json`.

A route that answers HTML becomes a page: `/about` is written to `about/index.html`, which GitHub serves at `/about`.

Call JSON routes without a trailing slash. `@Controller('/api/posts')` with `@Get('/')` is exported as the file `api/posts`: GitHub serves it at `/api/posts`, and answers `/api/posts/` with a 404, where the server accepts both.

Two routes cannot both be exported when one is a path under the other: `/api/posts` and `/api/posts/1` would need `api/posts` to be a file and a directory at once. The build reports the second one. Render lists and items under different prefixes, for example `/api/posts` and `/api/post/1`.

## Project sites and the base path

A project site lives under the repository name: `https://<user>.github.io/<repo>/`. The files are the same, but every absolute URL in your frontend has to start with `/<repo>/`:

```ts
const posts = await fetch(`${import.meta.env.BASE_URL}api/posts`).then((response) => response.json());
```

With Vite, set `base: '/<repo>/'` in `vite.config.ts`, which is where `import.meta.env.BASE_URL` comes from. A user site (`<user>.github.io`) or a custom domain is served from `/` and needs none of this.

## The workflow

```yaml [.github/workflows/pages.yml]
name: Pages

on:
  push:
    branches: [main]
  workflow_dispatch:

permissions:
  contents: read
  pages: write
  id-token: write

concurrency:
  group: pages
  cancel-in-progress: true

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v6
      - uses: pnpm/action-setup@v4
      - uses: actions/setup-node@v6
        with:
          node-version: 24
          cache: pnpm
      - run: pnpm install --frozen-lockfile
      - run: pnpm run build:pages
      - uses: actions/upload-pages-artifact@v4
        with:
          path: dist-static

  deploy:
    needs: build
    runs-on: ubuntu-latest
    environment:
      name: github-pages
      url: ${{ steps.deployment.outputs.page_url }}
    steps:
      - id: deployment
        uses: actions/deploy-pages@v4
```

## Files GitHub leaves out

`actions/upload-pages-artifact` does not upload files and directories whose name starts with a dot. A `public/.well-known/security.txt` is in `dist-static` and not on the site. Serve such files from a host you control, or publish from a branch instead of the workflow (the export writes `.nojekyll` for that case, so GitHub does not run Jekyll over the files).

## What does not work

- Any route that is not a `GET`, and any `GET` whose answer depends on the request.
- `@Sse()` and `@Stream()` routes as live streams. A stream that ends is saved like any other answer, and one still going after 30 seconds is stopped and reported.
- Middlewares at request time: authentication, rate limiting and response headers set by the application are not there, because the application is not. A route behind `@Auth()` answers 401 during the build and is reported as not exported.
- Fresh data. The files hold what the routes answered when the workflow ran. Run it on a schedule (`on: schedule`) or after a content change to refresh them.

For a fullstack project, publish the web app with its own build and point it at an API deployed elsewhere: the recipe is for an API project and says so when applied to another layout.
