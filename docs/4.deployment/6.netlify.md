title: Netlify
description: Deploy your Vercube application as a Netlify Function behind Netlify's CDN
---

On Netlify the application runs as one Function that answers every path, and the files in `public/` are served by Netlify's CDN before the function is asked. The adapter in `@vercube/serverless/netlify` uses the Web `Request` / `Response` signature of Netlify Functions 2.0, so nothing is converted on the way.

## Setup

In a new project:

```sh
pnpm create vercube my-api --deploy netlify
```

In an existing one:

```sh
vercube add netlify
```

The recipe adds three things to the project.

A named export in the entry, and the configuration in the bundle:

```ts [src/index.ts]
import { useContainer } from '@/boot/Container';
import { createApp, provideConfig, type App } from '@vercube/core';
import { toServerlessHandler, type NetlifyHandler } from '@vercube/serverless/netlify';
import config from '../vercube.config';

provideConfig(config);

const app: App = await createApp();
app.container.expand(useContainer);

if (import.meta.main) {
  await app.listen();
}

export const netlify: NetlifyHandler = toServerlessHandler(app);
```

`provideConfig(config)` is there because the function bundle does not carry `vercube.config.ts` as a file: importing it puts it in the bundle, and `provideConfig` hands it to `createApp()`. `.env` files are not read either, set variables in the Netlify UI or with `netlify env:set`.

The function, which is the built application and a path:

```ts [netlify/functions/api.mts]
import { netlify } from '../../dist/index.mjs';
import type { Config } from '@netlify/functions';

export default netlify;

// every path that is not a file in `public`
export const config: Config = { path: '/*', preferStatic: true };
```

And the build settings:

```toml [netlify.toml]
[build]
  command = "vercube build"
  publish = "public"

[functions]
  directory = "netlify/functions"
  node_bundler = "esbuild"
```

```sh
pnpm dev          # vercube dev, on Node, with reload
pnpm preview      # the built function behind Netlify's local CDN, at http://localhost:8888
pnpm run deploy   # netlify deploy --build --prod (run `netlify login` and `netlify link` once)
```

With `path: '/*'` and `preferStatic: true`, `GET /logo.png` is answered from `public/logo.png` without starting the function, and `GET /api/users` reaches your controller. To keep the application under a prefix, narrow the path (`path: '/api/*'`) and Netlify answers everything else itself.

## The request context

Netlify passes a context with each request: where the visitor is, their address, the deploy and the site. Read it through `NetlifyContext`, typed with `Context` from `@netlify/functions`:

```ts [src/controller/WhereController.ts]
import { Controller, Get } from '@vercube/core';
import { Inject } from '@vercube/di';
import { NetlifyContext } from '@vercube/serverless/netlify';
import type { Context } from '@netlify/functions';

@Controller('/where')
export class WhereController {
  @Inject(NetlifyContext)
  private readonly netlify!: NetlifyContext<Context>;

  @Get('/')
  where() {
    const { geo, ip } = this.netlify.context;

    return { country: geo?.country?.code, city: geo?.city, ip };
  }
}
```

`NetlifyContext` is a service like any other and has to be bound before a controller injects it, in `src/boot/Container.ts` (the recipe adds the line):

```ts [src/boot/Container.ts]
container.bind(NetlifyContext);
```

`context` throws when read outside a request, for example in a constructor or an `@Init()` method. `waitUntil(promise)` keeps the invocation alive for work that outlasts the response, such as an analytics call.

## What is different on Netlify

- **A function has a time limit.** A synchronous function may run for up to 60 seconds, and a response has to start within that time. A stream that outlives the limit is cut.
- **No process between requests.** An instance is frozen after it answers and may be thrown away. Connections that expect a live process (a queue consumer, a WebSocket server, a Redis subscription) do not work: use drivers that open a connection per request, or a service with an HTTP API.
- **The scheduler needs Netlify's.** `@vercube/scheduler` keeps timers in a running process. Use a [scheduled function](https://docs.netlify.com/build/functions/scheduled-functions/) that calls the code the job would run.
- **Compression is Netlify's.** The [`compression`](/docs/core-features/configuration#response-compression) setting is ignored: the CDN compresses responses and negotiates the encoding with the client.
- **Static files are the CDN's.** Files in `public/` are published with the deploy. The application's own static file handler has nothing to read inside the function.

## Edge Functions

Netlify Edge Functions run on Deno at the edge. The same handler works there, as its signature is the same:

```ts [netlify/edge-functions/api.ts]
import { netlify } from '../../dist/index.mjs';

export default netlify;

export const config = { path: '/api/*' };
```

This is not what the recipe sets up and it is not part of the test suite. Edge Functions have a smaller CPU budget and no Node APIs beyond the ones Deno provides, so use it for an application that is small and has no Node-only dependency.

## CI

Netlify builds and deploys on every push once the repository is linked, with the settings from `netlify.toml`. To deploy from your own pipeline instead:

```yaml [.github/workflows/deploy.yml]
name: Deploy
on:
  push:
    branches: [main]

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v6
      - uses: pnpm/action-setup@v4
      - uses: actions/setup-node@v6
        with:
          node-version: 24
          cache: pnpm
      - run: pnpm install --frozen-lockfile
      - run: pnpm run deploy
        env:
          NETLIFY_AUTH_TOKEN: ${{ secrets.NETLIFY_AUTH_TOKEN }}
          NETLIFY_SITE_ID: ${{ secrets.NETLIFY_SITE_ID }}
```
