title: Overview
description: A local-first inspector for Vercube applications - dependency graph, routes, request waterfalls, logs and audits
---

Devtools serve an inspector from your running application: the DI container, the route table, request waterfalls, logs, storage, resolved config and an audit. It is one self-contained HTML page served by the app itself, with no outbound traffic and no separate process.

## Installation

::code-group
  ```bash [pnpm]
  $ pnpm add -D @vercube/devtools
  ```
  ```bash [npm]
  $ npm install --save-dev @vercube/devtools
  ```
  ```bash [bun]
  $ bun install --dev @vercube/devtools
  ```
::

Register the plugin in `vercube.config.ts` and open `http://localhost:3000/_devtools`.

```ts [vercube.config.ts]
import { defineConfig } from '@vercube/core';
import { DevtoolsPlugin } from '@vercube/devtools';

export default defineConfig({
  plugins: [DevtoolsPlugin],
});
```

::note
`app.addPlugin(DevtoolsPlugin)` inside `createApp({ setup })` also works, but attaches after the container is built, so container construction and process metrics will be missing.
::

Panels are in the left rail, the first ten with number shortcuts `1` to `9` and `0`. The active panel is written to the URL hash, so `/_devtools#requests` is shareable. The buttons at the bottom pause the live stream, download a JSON snapshot of everything, and switch the theme.

## Overview

![Vercube Devtools, Overview panel](/images/devtools/overview.webp)

Answers "what am I connected to and is it healthy": name, version, mode, runtime, uptime, counts of routes, services and plugins, live throughput, CPU, heap, event loop delay and active handles. Every summary cell opens the panel behind it.

Handy when several apps run on neighbouring ports and you are about to debug the wrong one.

## Requests

![Vercube Devtools, Requests panel](/images/devtools/requests.webp)

Answers "where did the time go". Every request is recorded with the status the client observed, and opening one gives a waterfall: a span per middleware, one for the handler, and the framework time left over for routing, argument resolution and serialization. The log lines written during that request, the bodies and the headers are below it.

Bodies are read from a clone of the message, so recording never touches the stream your app consumes. Headers such as `authorization` and `cookie` are redacted, and so are credential-looking fields in JSON and urlencoded bodies. Other bodies are recorded as they are, so on an app that sends secrets in them:

```ts [vercube.config.ts]
plugins: [withPluginOptions(DevtoolsPlugin, { captureBodies: false })],
```

## Logs

![Vercube Devtools, Logs panel](/images/devtools/logs.webp)

Everything written through the `Logger` service, filterable by level and stamped with the request that produced it. The search matches structured context, not just the message, so given:

```ts
this.logger.info('order created', { orderId, userId });
```

typing an order id finds that line, and the request id next to it takes you to the call that wrote it. A bare `console.log` bypasses the `Logger` service and never shows up here.

## Storage

![Vercube Devtools, Storage panel](/images/devtools/storage.webp)

Keys held by every `@vercube/storage` mount, with the value behind a key on click, plus the defaults `@vercube/cache` runs with. Read-only: it lists and previews, it never writes.

The usual use is confirming that a `@Cache({ maxAge: 300 })` entry is really in the store, under the key you expect, with the value you expect. Values under credential-looking keys are never read back.

## Queues

![Vercube Devtools, Queues panel](/images/devtools/queues.webp)

Every mounted transport, every queue with a handler, and the counters behind them: published, processed, failed, retried, unhandled. Opening a queue lists its handlers and, on a transport that supports it, the messages waiting on it, without consuming any of them.

Individual jobs are not listed here. `@vercube/queue` traces them, so a job appears in Requests as a consumer span parented on the request that queued it, however long ago and in whichever process that happened.

## Routes

![Vercube Devtools, Routes panel](/images/devtools/routes.webp)

The route table as the router sees it, grouped by controller. Opening a route shows its decorated arguments, whether each one is validated, and the middleware chain in execution order with phases and priorities, which is the fastest answer to "why is this middleware running here" and "why does this path 404".

An argument marked unvalidated means the payload reaches the handler unchecked:

```ts
@Post('/orders')
public create(@Body({ validationSchema: OrderSchema }) body: Order) {}
```

### Playground

Open a route and switch to the **Playground** tab to call it without leaving devtools. The form is built from what the handler reads: one input per path value, one per `@QueryParam()` and `@Header()`, and a body editor for `@Body()`. The URL above the form changes as you type.

```ts
@Put('/orders/:id')
public update(
  @Param('id') id: string,
  @Body({ validationSchema: OrderSchema }) order: Order,
  @QueryParams({ validationSchema: OrderQuerySchema }) query: OrderQuery,
  @Header('x-tenant') tenant?: string,
) {}
```

For this route the form asks for `id`, lists the properties of `OrderQuerySchema` as query inputs with the required ones marked, offers `x-tenant`, and starts the body from an example generated from `OrderSchema`:

```json
{
  "sku": "string",
  "quantity": 1,
  "note": "string",
  "gift": false
}
```

While you edit, the body and the query are checked against those schemas and the problems are listed under the field, for example `quantity must be at least 1`. You can still send an invalid request to see what the server answers. The schemas come from the validation library through the Standard Schema JSON Schema interface (`schema['~standard'].jsonSchema`), which zod 4 provides. Any library that implements it works the same way. A schema that cannot describe itself leaves the editor empty and nothing is checked. The body can also be sent as plain text or as form data.

**Send** issues the request from your browser to the application, on the same origin, so cookies, CORS and proxies behave as they do for your frontend. `GET` and `HEAD` are sent at once. `POST`, `PUT`, `PATCH` and `DELETE` first show the method and the final URL and wait for a second click, or for Enter. Nothing is ever sent by opening a link: the playground reads nothing from the URL, and loading an entry from the history only fills the form.

The response shows the status, the time until the headers arrived, the total time, the size, the headers and the body. JSON is pretty printed, other text is shown as it is, and a binary body becomes a download. An `@Sse()` route streams its events into the panel until you press **Stop**.

Every playground request carries an `x-devtools-playground` header and a `traceparent` header with a trace id the playground picked. **Open in Requests** uses that id to select the request in the Requests view, with its timeline, its logs and its captured bodies. Requests sent from the playground carry a `playground` mark in that list. For a stream the button works once the stream has ended, because that is when its trace ends.

Credentials for secured routes are entered once under **Credentials**: a bearer token, basic credentials, an API key in a header of your choice, or a cookie. They are sent with secured routes by default and with any other route when you tick **Send with this request**. They stay in memory until you close the page. Tick **Remember on this device** to keep them in `localStorage`, and untick it to remove them again. They are never written to the URL, to the history or to the devtools stream, and the header you chose for an API key is redacted in the Requests view like `authorization` is. A browser does not let a page set the `Cookie` header, so a cookie is placed in the cookie jar for the duration of the request and removed afterwards.

The last 15 requests per route are listed under **History**, and **Save this request** keeps one under a name. Both live in the `localStorage` of your browser and never reach the server. **Copy as curl** and **Copy as fetch** export the request as it would be sent. Credentials are left out of the copy unless you tick **Include credentials in copies**.

The playground can be turned off, or kept away from some routes, with the [`playground` option](/docs/modules/devtools/configuration#route-playground). WebSocket routes, queue jobs and scheduled jobs are not called from here. The Queues and Scheduler views have their own actions.

## Graph

![Vercube Devtools, Graph panel](/images/devtools/graph.webp)

The container drawn as a graph: nodes by role, arrows from a dependent to its dependency, hollow nodes for bindings nothing has resolved, rings around dependency cycles. Selecting a service lists what it injects and what injects it, both clickable, which is the blast radius to check before changing a constructor.

An `@Inject` of a key nothing binds is marked unbound here before it throws at runtime. Inspecting never instantiates anything.

## Config

![Vercube Devtools, Config panel](/images/devtools/config.webp)

The configuration the framework actually resolved, after defaults, files and environment were merged, flattened to dotted paths such as `server.port`. Search matches paths and values, so a port number finds whichever setting holds it.

Values whose key reads like a credential are replaced with `<redacted>`. The rule is name-based, so a secret inside a connection string is still shown.

## Health

What the [readiness probe](/docs/core-features/health) would answer, and why. The application state (`starting`, `ready`, `draining`), every registered check grouped by the module that added it (`queue:orders` under queue, your own under application), whether a failure makes the application not ready or only degraded, how long the check took against its timeout, and the error of the ones that are down. A check that needed more than half of its timeout is marked before it starts failing.

The panel reads `app.health` directly, so it works with `health` off, when there are no probe routes to curl. **Run checks** runs them now, past the report cache, and the same call is a POST away:

```bash
curl -s -X POST -H 'x-devtools-request: 1' localhost:3000/_devtools/api/health/check | jq '.report.checks | map_values(.status)'
```

Running the checks calls the backends they watch, so the panel runs them once when it opens without a report and after that only when asked: the automatic re-run is off until you pick an interval, which is then remembered. Nothing runs while the application is starting or draining, the same as the probe. Every run is a `health.check` trace in the Requests panel, with one event per check, and the errors and details of the checks are part of a snapshot as they are, so look before sharing one. The strip at the bottom is the configuration in effect: the probe paths, `details`, `timeout`, `cacheTtl`, and the `drainDelay` and `handleSignals` that `health` switches on. The token is never shown, only that one is set.

## Where the data comes from

Devtools does not collect anything of its own. It registers an OpenTelemetry span processor, a metric reader and a log drain, and reads structural data from core's [introspection registry](/docs/core-features/introspection). Two consequences are worth knowing.

The first is that instrumenting a package makes it visible here for free. A storage read, a cache lookup, an authentication decision and your own `telemetry.span()` calls all appear in the request waterfall, nested where they happened, without devtools knowing those packages exist.

The second is that container construction is a trace like any other. Startup shows up in the request list as a `vercube.bootstrap` trace whose children are the services that were built, so the same waterfall that explains a slow request explains a slow boot.

The wire format is OTLP, the same bytes an OpenTelemetry collector would receive. Enabling devtools turns telemetry on automatically; see [Telemetry](/docs/modules/telemetry/overview) if you also want to export it somewhere.

## Audit

![Vercube Devtools, Audit panel](/images/devtools/audit.webp)

Rules over the container, the router and recorded traffic, scored 0-100:

| Rule                              | Severity | What it catches                                             |
| --------------------------------- | -------- | ------------------------------------------------------------- |
| `di/unbound-dependency`           | error    | `@Inject` of a key nothing binds, so resolution will throw     |
| `router/duplicate-route`          | error    | The same method and path registered twice                      |
| `runtime/server-errors`           | error    | Recorded requests that returned 5xx                            |
| `di/circular-dependency`          | warning  | Dependency loops in the container                              |
| `validation/missing-schema`       | warning  | `@Body()` or `@QueryParams()` reaching a handler unvalidated   |
| `bootstrap/slow-service`          | warning  | Constructors that dominate startup                             |
| `runtime/slow-requests`           | warning  | Requests over 500ms                                            |
| `di/unbound-optional-dependency`  | info     | `@InjectOptional` that will always resolve to `null`           |
| `di/unused-service`               | info     | Bindings nothing has ever resolved                             |

Runtime rules only see what devtools recorded, so drive some traffic before trusting them.

## Snapshot and JSON

**Snapshot** downloads one JSON file with the overview, the audit, every introspection section and the buffered traces, metrics and logs: the exact state the UI is showing, and the right thing to attach to a bug report.

Everything the UI reads is plain JSON under the mount, so the same data works outside the browser:

```bash
curl -s localhost:3000/_devtools/api/audit | jq '{score, errors: .counts.error}'
curl -s localhost:3000/_devtools/api/introspect/routes | jq '.data | length'
curl -s localhost:3000/_devtools/api/signals/traces \
  | jq '[.resourceSpans[].scopeSpans[].spans[].name] | unique'
```

::warning
Snapshots contain configuration, storage keys, headers and bodies. Credential-looking entries are redacted, application data is not.
::

## Overhead

Devtools adds no instrumentation of its own; it subscribes to telemetry that is already there, and telemetry is off by default outside development. Its own traffic is excluded from what it records, so the inspector never appears in the data it is inspecting.

Buffers are bounded and metrics are only collected while a browser is connected, so a dev server left running overnight does not grow without limit.

Devtools are off in production builds unless you enable them explicitly, and then only behind a token. See [Configuration](/docs/modules/devtools/configuration).
