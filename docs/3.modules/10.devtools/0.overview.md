The Devtools module serves an in-process inspector from your running application. Open `/_devtools` for the dependency graph, route table, request waterfalls with bodies and logs, process metrics, resolved config, storage, bootstrap flamegraph and audit findings — all as a single self-contained HTML page with no outbound traffic.

## Installation

::code-group
  ```bash [pnpm]
  $ pnpm add -D @vercube/devtools
  ```
  ```bash [npm]
  $ npm install --save-dev @vercube/devtools
  ```
  ```bash [bun]
  $ bun install --dev @vercube/devtools
  ```
::

## Quick Start

::steps
### Register the plugin

Add it to the `plugins` array of your config. The `configure` phase runs before the container is created, so the bootstrap profiler can observe the first service constructions.

```ts [vercube.config.ts]
import { defineConfig } from '@vercube/core';
import { DevtoolsPlugin } from '@vercube/devtools';

export default defineConfig({
  plugins: [DevtoolsPlugin],
});
```

### Open the inspector

Start your app and go to `http://localhost:3000/_devtools`. Panels are reachable with the number keys `1` to `9`.

::

::note
`app.addPlugin(DevtoolsPlugin)` inside `createApp({ setup })` also works, but attaches after the container is built, so the bootstrap profile will be incomplete. The Bootstrap panel reports when that happened.
::

## What you get

### Container graph

Every binding in the container, drawn as a force-directed graph and coloured by role (controller, middleware, service, plugin, value or framework). Click a node to see its dependencies, dependents, whether a singleton exists, and construction cost.

The graph is derived from container metadata and prototype decorations — inspecting never instantiates unresolved services. Circular dependencies are highlighted and each loop is reported once.

### Route explorer

Routes registered in the router, grouped by controller. Expanding a route shows handler arguments (decorator and validation) and the middleware chain in execution order, with priorities and global markers.

### Request inspector

Every request is recorded with the status and duration the client observed, including error-handler responses. Selecting one shows a waterfall per middleware and handler, plus query parameters, headers and bodies. JSON is pretty-printed; the inspector width is adjustable.

Bodies are read from a message clone so the app stream is untouched, and they never delay the response. Binary payloads are described, streaming responses are skipped, and bodies over `maxBodyBytes` are truncated or omitted. New requests stream in over SSE.

::warning
Credential-bearing headers (`authorization`, `cookie`, API keys) are always replaced with `<redacted>`; use `redactHeaders` to add your own. Bodies cannot be redacted by name — set a `token` or turn `captureBodies` off when that matters.
::

### Process metrics

CPU, heap, event loop delay and active handles, sampled every two seconds while a stream is open and stopped when the last one closes.

Event loop delay is reported above the histogram sampling floor (`monitorEventLoopDelay` resolution), so an idle loop does not appear as constant lag.

### Logs

Lines written through the `Logger` service, kept in a ring buffer and filterable by level. Each line is correlated with the in-flight request when present.

Capture wraps the `Logger` instance in the container without re-initialising evlog. evlog's per-request wide event is not captured; method, path, status and duration are already recorded natively.

### Storage

Mounted `@vercube/storage` instances (driver, key count and keys) plus `@vercube/cache` defaults. Both packages are optional and discovered by name in the container; nothing is instantiated for inspection, so unused storage is reported as absent.

### Config

The resolved configuration: the `runtime` section and the merged `vercube.config.ts`, flattened to dotted paths. Credential-looking keys are replaced with `<redacted>`.

### Bootstrap profiler

A flamegraph of container construction. Nested resolve intervals rebuild the call tree; self time is total minus time spent building dependencies. Hotspots are ranked by self time.

### Audit

A set of static and runtime rules, scored 0-100:

| Rule                              | Severity | What it catches                                            |
| --------------------------------- | -------- | ---------------------------------------------------------- |
| `di/unbound-dependency`           | error    | `@Inject` of a key nothing binds - resolution will throw    |
| `router/duplicate-route`          | error    | The same method and path registered twice                   |
| `runtime/server-errors`           | error    | Requests that returned 5xx                                  |
| `di/circular-dependency`          | warning  | Dependency loops in the container                           |
| `validation/missing-schema`       | warning  | `@Body()` or `@QueryParams()` reaching a handler unvalidated |
| `bootstrap/slow-service`          | warning  | Constructors that dominate startup                          |
| `runtime/slow-requests`           | warning  | Requests over 500ms                                         |
| `di/unbound-optional-dependency`  | info     | `@InjectOptional` that will always resolve to `null`        |
| `di/unused-service`               | info     | Bindings nothing has ever resolved                          |

### Snapshot

The **Snapshot** button downloads one JSON file with overview, graph, routes, bootstrap profile, audit, configuration, requests and logs.

## Configuration

```ts [vercube.config.ts]
import { defineConfig, withPluginOptions } from '@vercube/core';
import { DevtoolsPlugin } from '@vercube/devtools';

export default defineConfig({
  plugins: [
    withPluginOptions(DevtoolsPlugin, {
      path: '/__inspect',
      token: process.env.DEVTOOLS_TOKEN,
      maxRequests: 500,
      redactHeaders: ['x-internal-signature'],
    }),
  ],
});
```

| Option           | Type                | Default        | Description                                                        |
| ---------------- | ------------------- | -------------- | ------------------------------------------------------------------ |
| `enabled`        | `boolean`           | `config.dev`   | Master switch. Off in production unless explicitly enabled.         |
| `path`           | `string`            | `'/_devtools'` | Where the UI and its API are mounted.                               |
| `token`          | `string \| null`    | `null`         | Required as `?token=` or an `x-devtools-token` header when set.     |
| `maxRequests`    | `number`            | `250`          | Size of the in-memory request ring buffer.                          |
| `trackRequests`  | `boolean`           | `true`         | Record per-request timelines.                                       |
| `captureHeaders` | `boolean`           | `true`         | Capture request and response headers.                               |
| `redactHeaders`  | `string[]`          | `[]`           | Extra header names to redact on top of the built-in list.           |
| `captureBodies`  | `boolean`           | `true`         | Capture request and response bodies for the inspector.              |
| `maxBodyBytes`   | `number`            | `65536`        | Largest body kept per message.                                      |
| `captureLogs`    | `boolean`           | `true`         | Capture lines written through the `Logger` service.                 |
| `maxLogs`        | `number`            | `500`          | Size of the in-memory log ring buffer.                              |

## Security

Devtools expose the internal structure of your application: service names, route paths, middleware chains, configuration, storage keys, recent traffic and log lines. Because of that:

- they are **disabled unless `config.dev` is true**, and stay disabled when `production` is also set;
- turning them on elsewhere requires an explicit `enabled: true`;
- set a `token` whenever the app is reachable by anyone but you.

::warning
Devtools endpoints are ordinary `@Controller` routes, but the plugin detaches your application's **global** middlewares from them. Use the `token` option for access control instead of relying on app auth.
::

## Overhead

Devtools add three cheap hooks, confined to development:

- a DI container hook on each construction (no-op when unset);
- one pass over the route table on the first request to wrap middleware/handler methods and detach global middlewares from devtools routes;
- a wrap of the HTTP entry point to record status and duration.

Bootstrap profiling stops on the first request. The request buffer is bounded by `maxRequests`.
