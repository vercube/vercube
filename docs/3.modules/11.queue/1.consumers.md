A consumer is a container service that reads one queue. The class decorator says which queue, the method decorators say which jobs.

## @Consumer

Marks a class as the consumer of a queue and sets the defaults for every handler in it.

```ts
@Consumer({ queue: 'emails', concurrency: 5, attempts: 2, timeout: 10_000 })
export class EmailConsumer {}
```

| Option | Description |
| --- | --- |
| `queue` | Queue the class reads from. Required. |
| `strategy` | Mounted strategy to consume from. Defaults to `default`. |
| `concurrency` | How many jobs of this queue may run in parallel. Defaults to 1. |
| `attempts` | Default attempts for every handler of the class. |
| `backoff` | Default backoff for every handler of the class. |
| `timeout` | Default time limit for every handler of the class. |
| `schema` | Default payload schema for every handler of the class. |

The queue starts being consumed when the class is bound in the container:

```ts
container.bind(EmailConsumer);
```

Nothing happens without that binding, exactly like a controller that is never bound. A handler declared on a subclass inherits the queue of its base class, so shared consumer bases work as expected.

## @Job

Marks a method as the handler of one job name. The method receives the payload and the job context.

```ts
@Consumer({ queue: 'emails' })
export class EmailConsumer {
  @Job('welcome')
  public async welcome(payload: { userId: string }, context: QueueTypes.JobContext): Promise<void> {
    context.logger?.info(`attempt ${context.attempt} of ${context.attempts}`);

    await this.gMailer.sendWelcome(payload.userId);
  }
}
```

Options given here override the ones the class declared:

| Option | Description |
| --- | --- |
| `attempts` | Total attempts, the first one included. Applies when the published job carries no `attempts` of its own. |
| `backoff` | Delay between attempts. A number is a fixed delay in milliseconds, `{ type: 'exponential', delay }` doubles it every attempt. |
| `timeout` | Milliseconds after which the attempt is failed. |
| `schema` | Standard Schema validating the payload before the handler runs. |

Returning marks the job done, throwing marks the attempt failed. There is nothing to acknowledge by hand.

## Where the job name comes from

A job name is not a broker concept. It is a label the module writes into the message metadata, so that one queue can carry several kinds of work, each with its own handler, retries and schema. Every transport keeps it where it naturally belongs:

| Transport | Job name lives in |
| --- | --- |
| BullMQ | the native job name |
| RabbitMQ | the `type` message property, falling back to the `x-job` header |
| Kafka | the `x-job` record header |
| Memory | the job record |

So a job published as `add({ queue: 'emails', job: 'welcome', payload: { userId } })` arrives on RabbitMQ as an ordinary AMQP message whose body is the payload and whose `type` is `welcome`:

```
queue: emails
properties:
  type:      'welcome'
  messageId: '0f2c…'
  headers:   { x-job: 'welcome', x-attempt: '1' }
body: {"userId":"u-42"}
```

If a queue only ever carries one kind of work, the name is close to cosmetic: declare a single `@Job('process')` and be done. Modelling it the other way round, one queue per job, works just as well.

::warning
A message produced by something other than this module carries no job name, so it resolves to `unknown` and, with the default `onUnhandled: 'ignore'`, is acknowledged and dropped with a warning. When plugging into a queue somebody else fills, pick one of these:

- have the producer set the job name (`type` on RabbitMQ, the `x-job` header on Kafka),
- register the handler as `@Job('unknown')`, which is exactly the name those messages resolve to,
- or set `onUnhandled: 'fail'` so nothing is dropped silently and the transport dead-letters it instead.
::

## The job context

The second argument describes the attempt being processed.

```ts
@Job('report')
public async report(payload: Report, context: QueueTypes.JobContext<Report>): Promise<void> {
  // where it came from
  context.queue;     // 'reports'
  context.job;       // 'report'
  context.strategy;  // name of the mounted strategy
  context.id;        // job id, as assigned by the transport
  context.headers;   // transport headers received with the job

  // which attempt this is
  context.attempt;   // 1 on the first run
  context.attempts;  // how many attempts this job may take

  // reporting back
  context.logger?.info('halfway');
  await context.updateProgress(50);

  // the transport-native job, when you really need it
  context.raw;
}
```

`updateProgress()` is a no-op on transports that do not track progress, so calling it is always safe. `context.logger` is the application logger with the queue, job, id and attempt already attached, and is null when no logger is bound.

## Validating payloads

A job payload comes from outside the process, so it deserves the same treatment as a request body. Pass any [Standard Schema](https://standardschema.dev) and the payload is validated before the handler runs.

```ts
import { z } from 'zod';

const WelcomeSchema = z.object({ userId: z.string().uuid() });

@Consumer({ queue: 'emails' })
export class EmailConsumer {
  @Job('welcome', { schema: WelcomeSchema })
  public async welcome(payload: z.infer<typeof WelcomeSchema>): Promise<void> {}
}
```

The handler receives the parsed value, so defaults and coercions the schema applies are visible inside it. A payload that does not match fails the job without retrying it.

::note
Validation needs a `ValidationProvider` in the container, which `@vercube/core` binds by default. A job declaring a schema in a container without one fails with a clear error instead of running unvalidated.
::

## Lifecycle hooks

`@OnJobCompleted()` and `@OnJobFailed()` observe the queue of their consumer class. A hook never changes the outcome of a job: if a hook throws, the throw is logged and forgotten.

```ts
@Consumer({ queue: 'emails' })
export class EmailConsumer {
  @Job('welcome', { attempts: 3 })
  public async welcome(payload: { userId: string }): Promise<void> {}

  @OnJobCompleted()
  public async sent(context: QueueTypes.JobContext): Promise<void> {
    this.gMetrics.increment(`emails.${context.job}.sent`);
  }

  @OnJobFailed()
  public async failed(error: Error, context: QueueTypes.JobContext): Promise<void> {
    // called once per failed attempt, so tell a retry from a final failure
    if (context.attempt === context.attempts) {
      await this.gAlerts.report(error, context.id);
    }
  }
}
```

Both accept a job filter when a hook should only watch one kind of job:

```ts
@OnJobFailed({ job: 'digest' })
public async digestFailed(error: Error): Promise<void> {}
```

## Concurrency

`concurrency` is per queue and per process. The highest value requested by any handler of a queue wins, and the manager's `concurrency` setting is the floor for every queue.

```ts
// up to 10 jobs of 'emails' at a time in this process
@Consumer({ queue: 'emails', concurrency: 10 })
export class EmailConsumer {}
```

On BullMQ it becomes the worker concurrency, on RabbitMQ the channel prefetch, on Kafka the number of partitions consumed concurrently, and in memory the number of handlers running at once.

## Registering handlers by hand

The decorators are a thin layer over `QueueManager.registerConsumer()`. Consumers built at runtime can call it directly:

```ts
queueManager.registerConsumer({
  strategy: 'default',
  queue: 'emails',
  job: 'welcome',
  handler: async (payload, context) => this.send(payload),
  options: { attempts: 3 },
  concurrency: 2,
  source: 'runtime',
});
```

Registering a second handler for the same job of the same queue is an error, so a copy-pasted job name fails loudly instead of silently shadowing the first handler.
