title: Strategies
description: Memory, BullMQ, RabbitMQ and Kafka transports, their options and their limits
---

A strategy owns the connection to one broker and translates between its vocabulary and the module's job model. Everything else - routing, validation, retries, timeouts, hooks and counters - lives in the manager, so a strategy stays small and every transport behaves the same way.

## What each transport can do

| | Memory | BullMQ | RabbitMQ | Kafka |
| --- | --- | --- | --- | --- |
| Native retries | no | yes | no | no |
| Native delay | yes | yes | no | no |
| Priority | yes | yes | yes | no |
| Progress | yes | yes | no | no |
| Counters | yes | yes | yes | yes |

`no` does not mean unsupported: everything the transport cannot do is either emulated by the manager, or documented below as a real limit. The manager only stops emulating retries when the transport owns them, which is how a BullMQ job keeps its attempts in Redis instead of being republished.

## Mounting

Every strategy is mounted by name, so an application can talk to several brokers at once.

```ts
app.addPlugin(QueuePlugin, {
  strategies: [
    defineQueueStrategy({ strategy: BullMQStrategy, initOptions: { connection } }),
    defineQueueStrategy({ name: 'events', strategy: KafkaStrategy, initOptions: { client, groupId } }),
  ],
});
```

Each entry declares the options of its own strategy, and `defineQueueStrategy()` is what makes TypeScript check that pairing. Without it the entry still works, but `initOptions` goes unchecked: a plain array gives TypeScript nothing to infer the strategy from.

The first mount has no name, which makes it `default`. Anything that does not name a strategy uses it:

```ts
await queue.add({ queue: 'emails', job: 'welcome', payload });                     // default
await queue.add({ strategy: 'events', queue: 'orders', job: 'placed', payload });  // kafka
```

```ts
@Consumer({ queue: 'orders', strategy: 'events' })
export class OrderConsumer {}
```

## MemoryStrategy

Jobs live in the running process and are gone when it stops. This is the strategy for tests, for examples and for work that may be lost on a restart. It is also the reference implementation: delays, priorities and progress behave exactly as documented.

```ts
import { MemoryStrategy } from '@vercube/queue/strategies/MemoryStrategy';

await queueManager.mount({ strategy: MemoryStrategy });
```

It needs no options. For tests it adds one method the other strategies do not have:

```ts
const memory = queueManager.getStrategy() as MemoryStrategy;

await queueManager.add({ queue: 'emails', job: 'welcome', payload: { userId: '1' } });
await memory.idle(); // resolves once nothing is waiting, delayed or running

expect(sent).toHaveLength(1);
```

## BullMQStrategy

Redis keeps the jobs and BullMQ owns their lifecycle: attempts, backoff, delays, priorities, progress and the completed and failed sets.

```ts
import { BullMQStrategy } from '@vercube/queue/strategies/BullMQStrategy';

await queueManager.mount({
  strategy: BullMQStrategy,
  initOptions: {
    connection: { host: '127.0.0.1', port: 6379 },
    prefix: 'my-app',
    defaultJobOptions: { removeOnComplete: 1000, removeOnFail: 5000 },
  },
});
```

| Option | Description |
| --- | --- |
| `connection` | Redis connection options, or an existing ioredis client. Required. |
| `prefix` | Key prefix every queue lives under. |
| `defaultJobOptions` | BullMQ job options applied to every published job. |
| `queueOptions` | Extra options for every `Queue` the strategy creates. |
| `workerOptions` | Extra options for every `Worker` the strategy creates. |

::warning
Retries belong to the broker here, and BullMQ reads them from the job, not from the worker. `attempts` on `@Job()` is only a fallback for jobs published without any, so pass them when adding the job: `add({ ..., options: { attempts: 3, backoff: { type: 'exponential', delay: 1000 } } })`.
::

Jobs are stored as `{ payload, headers }` so the module's headers survive the round trip. A job added by another BullMQ producer, with plain data, is read as the payload itself.

## RabbitMQStrategy

Jobs are ordinary AMQP messages: the job name travels in the message `type` property, the module's bookkeeping in the headers, and the payload as JSON. Queues are declared as durable, and messages are published as persistent.

```ts
import { RabbitMQStrategy } from '@vercube/queue/strategies/RabbitMQStrategy';

await queueManager.mount({
  strategy: RabbitMQStrategy,
  initOptions: {
    url: 'amqp://localhost',
    queueOptions: { durable: true, deadLetterExchange: 'failed' },
  },
});
```

| Option | Description |
| --- | --- |
| `url` | Broker to connect to, as an `amqp://` URL or as connection fields. Required. |
| `socketOptions` | Socket options handed to amqplib. |
| `recovery` | Automatic reconnection, on by default. Pass options to tune the backoff, or `false` to fail fast. |
| `queueOptions` | Options every queue is asserted with. Defaults to `{ durable: true }`. |
| `publishOptions` | Options every message is published with. Defaults to `{ persistent: true }`. |
| `prefetch` | Unacknowledged messages a consumer may hold. Defaults to the consumer concurrency. |

Things worth knowing:

- A job whose attempts are exhausted is nacked without requeue, so it lands wherever the queue's dead letter exchange points. Declare one to keep failures instead of dropping them.
- Delays are kept by the manager on a timer, not by the broker, because a plain RabbitMQ has no delayed delivery. A process that stops before the timer fires loses the pending retry.
- Each consumed queue gets its own channel, so its prefetch is its own.
- Priorities only take effect on queues declared with `maxPriority`.

## KafkaStrategy

A queue is a topic. The job name travels in the `x-job` header and the payload is JSON.

```ts
import { KafkaStrategy } from '@vercube/queue/strategies/KafkaStrategy';

await queueManager.mount({
  strategy: KafkaStrategy,
  initOptions: {
    client: { clientId: 'orders', brokers: ['localhost:9092'] },
    groupId: 'orders-workers',
  },
});
```

| Option | Description |
| --- | --- |
| `client` | kafkajs client configuration: brokers, client id, ssl, sasl. Required. |
| `groupId` | Consumer group every consumer of this strategy joins. Required to consume. |
| `producer` | Extra producer configuration. |
| `consumer` | Extra consumer configuration, the group id excluded. |
| `send` | Send options applied to every produced record, such as `acks`. |
| `fromBeginning` | Start from the earliest offset when the group has no committed one. Defaults to false. |
| `onFailure` | `skip` logs a job the manager gave up on and moves the offset, `crash` stops the consumer. Defaults to `skip`. |

Things worth knowing:

- Kafka commits offsets rather than acknowledging single messages, so a failed job cannot be singled out. With the default `skip`, the offset moves on and the failure is logged and counted. With `crash`, the consumer stops and the partition waits, which is the right choice only when no job may ever be skipped.
- Ordering is per partition. Use the `key` job option to keep related jobs on the same partition: `add({ ..., options: { key: order.id } })`.
- Counters report how far the consumer group is behind the end of the topic, which needs a `groupId`.
- `publishMany()` produces the whole batch in a single request.

## Writing your own strategy

Extend `QueueStrategy` and implement four methods. Report what the transport can do through `capabilities`, and the manager fills in the rest.

```ts
import { QueueStrategy } from '@vercube/queue';
import type { QueueTypes } from '@vercube/queue';

export interface HttpStrategyOptions {
  endpoint: string;
}

export class HttpStrategy extends QueueStrategy<HttpStrategyOptions> {
  public readonly transport = 'http';

  public override get capabilities(): QueueTypes.Capabilities {
    return { retries: false, delay: false, priority: false, progress: false, stats: false };
  }

  public initialize(options: HttpStrategyOptions): void {
    this.fEndpoint = options.endpoint;
  }

  public async publish(request: QueueTypes.PublishRequest): Promise<QueueTypes.JobRef> {
    const response = await fetch(this.fEndpoint, {
      method: 'POST',
      headers: { 'content-type': 'application/json', ...request.headers },
      body: JSON.stringify(request.payload),
    });

    return { id: response.headers.get('x-id') ?? '', queue: request.queue, job: request.job, strategy: this.transport };
  }

  public async consume(request: QueueTypes.ConsumeRequest): Promise<QueueTypes.ConsumerHandle> {
    // call request.dispatch() for every job received, then hand back a way to stop
    return { queue: request.queue, stop: async () => this.fSource.close() };
  }

  public async close(): Promise<void> {
    await this.fSource.close();
  }
}
```

Two rules keep a custom strategy consistent with the built-in ones:

- `dispatch()` rejecting means the job failed for good. The manager has already run the hooks and applied the retry policy, so put nothing back on the queue: acknowledge it, discard it or dead-letter it.
- A strategy resolved through the container can use `@Inject`, so a logger or a config service is available like anywhere else.
