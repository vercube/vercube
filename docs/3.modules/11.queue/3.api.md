## QueuePlugin

Binds the `QueueManager` and mounts the strategies it is given.

```ts
app.addPlugin(QueuePlugin, {
  autoStart: true,
  concurrency: 1,
  onUnhandled: 'ignore',
  maxEvents: 50,
  strategies: [defineQueueStrategy({ strategy: MemoryStrategy })],
});
```

| Option | Default | Description |
| --- | --- | --- |
| `strategies` | `[]` | Strategies to mount when the application boots. Wrap each entry in `defineQueueStrategy()` to have its `initOptions` checked. |
| `autoStart` | `true` | Start consumers once the container is initialized. Set to false in producer-only processes. |
| `concurrency` | `1` | Default jobs processed in parallel per queue. |
| `onUnhandled` | `'ignore'` | What to do with a job no handler is registered for. `fail` reports it as failed so the transport can dead-letter it. |
| `maxEvents` | `50` | How many processed jobs are kept for inspection. |
| `capturePayloads` | `false` | Keep the payload and headers of failed attempts, so a failure can be diagnosed. `@vercube/devtools` turns this on for the session it inspects. |
| `maxPayloadBytes` | `4096` | Largest payload preview and stack trace kept, in bytes. |

## QueueManager

### mount()

Mounts a strategy under a name. The strategy is resolved through the container and connects on first use.

```ts
await queueManager.mount({ strategy: MemoryStrategy });
await queueManager.mount({ name: 'events', strategy: KafkaStrategy, initOptions: { client, groupId } });
```

`initOptions` is required when the strategy declares initialization options, optional when they include `undefined`, and rejected when the strategy takes none. The strategy is inferred from `strategy`, so passing the options of a different strategy is a compile error.

### defineQueueStrategy()

Type checks one mount and erases its options type, so a list of mounts of different strategies stays checked.

```ts
import { defineQueueStrategy } from '@vercube/queue';

app.addPlugin(QueuePlugin, {
  strategies: [
    defineQueueStrategy({ strategy: RabbitMQStrategy, initOptions: { url: 'amqp://localhost' } }),
    defineQueueStrategy({ name: 'events', strategy: KafkaStrategy, initOptions: { client, groupId } }),
  ],
});
```

::note
`mount()` checks `initOptions` on its own, because it infers the strategy from its argument. A plain array cannot: every entry holds a different strategy, and there is no inference site per entry. This helper is that site, and it compiles away to the object you passed it.
::

### add()

Adds a single job to a queue.

```ts
const ref = await queueManager.add({
  queue: 'emails',
  job: 'welcome',
  payload: { userId: '1' },
  options: { attempts: 3, backoff: { type: 'exponential', delay: 1000 }, delay: 5000 },
});

ref.id; // job id, as assigned by the transport
```

| Field | Description |
| --- | --- |
| `queue` | Queue the job is added to. |
| `job` | Name of the job, used to pick the handler. |
| `payload` | Payload handed to the handler. Must survive JSON serialization. |
| `strategy` | Mounted strategy to publish through. Defaults to `default`. |
| `options` | Per-job options, described below. |

Job options:

| Option | Description |
| --- | --- |
| `attempts` | Total attempts, the first one included. |
| `backoff` | Delay between attempts. A number is fixed milliseconds, `{ type: 'exponential', delay }` doubles it every attempt. |
| `delay` | Milliseconds before the job becomes available. |
| `priority` | Lower values are processed first. |
| `jobId` | Explicit id, used by transports that deduplicate on it. |
| `key` | Routing or partition key, keeping related jobs ordered on Kafka and RabbitMQ. |
| `headers` | Extra transport headers travelling with the job. |
| `removeOnComplete` | Whether completed jobs are kept, or how many, on transports that store history. |
| `removeOnFail` | Whether failed jobs are kept, or how many, on transports that store history. |

### addMany()

Adds many jobs of the same kind, using the transport's batch API when it has one.

```ts
await queueManager.addMany({
  queue: 'emails',
  job: 'digest',
  payloads: users.map((user) => ({ userId: user.id })),
});
```

### registerConsumer()

Registers a job handler. This is what `@Job()` calls.

```ts
queueManager.registerConsumer({
  strategy: 'default',
  queue: 'emails',
  job: 'welcome',
  handler: async (payload, context) => mailer.send(payload),
  options: { attempts: 3, timeout: 10_000, schema: WelcomeSchema },
  concurrency: 5,
  source: 'EmailConsumer.welcome',
});
```

Throws when a handler for the same job of the same queue already exists. Use `unregisterConsumer({ strategy, queue, job })` to remove one, which also stops the consumer once the queue has no handler left.

Registering under the job name `*` makes the handler the fallback of its queue, which is what `@AnyJob()` does. The exported `WILDCARD_JOB` constant holds that name, so nothing has to be spelled out by hand:

```ts
import { WILDCARD_JOB } from '@vercube/queue';

queueManager.registerConsumer({ strategy: 'default', queue: 'events', job: WILDCARD_JOB, handler, options: {}, source: 'ingest' });
```

### registerHook()

Registers a lifecycle hook. This is what `@OnJobCompleted()` and `@OnJobFailed()` call.

```ts
queueManager.registerHook('failed', {
  strategy: 'default',
  queue: 'emails',
  job: 'welcome',
  hook: async (error, context) => alerts.report(error, context.id),
  source: 'EmailConsumer.failed',
});
```

`unregisterHook(event, registration)` removes it again, given the very registration that was registered.

### start(), stop() and close()

```ts
await queueManager.start(); // connect every strategy and consume every queue that has a handler
await queueManager.stop();  // stop consumers, keep connections open so publishing still works
await queueManager.close(); // stop consumers and close every connection
```

All three are safe to call more than once. `start()` runs automatically after the container is initialized unless `autoStart` is false, and `close()` runs when the container is torn down.

### drain()

Waits for the work the manager scheduled in the background: consumers starting or stopping, and retries waiting for their backoff. Useful in tests and before a deliberate shutdown.

```ts
await queueManager.drain();
```

### stats()

Reads the counters a transport keeps for a queue. Transports that keep none return an empty object.

```ts
const stats = await queueManager.stats({ queue: 'emails' });

stats.waiting;   // jobs waiting to be processed
stats.active;    // jobs being processed
stats.completed; // completed jobs, on transports that store history
stats.failed;    // jobs that exhausted their attempts
stats.delayed;   // jobs waiting for their delay
```

### subscribe()

Follows every job the manager finishes, as it finishes it, instead of polling
`inspect()`. This is how the devtools panel stays live.

```ts
const stop = queueManager.subscribe((event) => {
  if (event.status === 'failed') {
    metrics.increment(`queue.${event.queue}.${event.job}.failed`);
  }
});

stop(); // removes the listener again
```

The listener gets the same event the inspection buffer keeps, so it carries the
outcome, the attempt, the duration and, for a failure, the error with its stack.
It is called even when `maxEvents` is 0, so a live view keeps working without any
buffer at all. A listener that throws is logged and kept, and never changes the
outcome of the job.

### inspect()

Describes what the module holds: mounted strategies, registered handlers, per-queue counters and the last processed jobs. This is what the devtools panel reads.

```ts
const snapshot = queueManager.inspect();

snapshot.started;    // whether consumers are running
snapshot.strategies; // one entry per mount, with its capabilities and status
snapshot.consumers;  // one entry per registered handler
snapshot.metrics;    // published, processed, failed, retried, unhandled and active, per queue
snapshot.events;     // recently processed jobs, newest first
```

### configure()

Sets manager-wide settings, merging into the existing ones. Per-job and per-handler options always win.

```ts
queueManager.configure({ concurrency: 4, onUnhandled: 'fail', maxEvents: 200 });
```

### getStrategy()

Returns a mounted strategy, for the rare case a transport-specific API is needed.

```ts
const bullmq = queueManager.getStrategy() as BullMQStrategy;
```

## Decorators

| Decorator | Applies to | Description |
| --- | --- | --- |
| `@Consumer(options)` | class | Declares the queue the class reads from and the defaults of its handlers. |
| `@Job(name, options?)` | method | Declares the method as the handler of one job name. |
| `@AnyJob(options?)` | method | Declares the method as the handler of every job the queue has no named handler for. |
| `@OnJobCompleted(options?)` | method | Runs after a job of the queue completed. |
| `@OnJobFailed(options?)` | method | Runs after an attempt of a job of the queue threw. |

See [Consumers](/docs/modules/queue/consumers) for the full description of each.

## JobContext

The second argument of every handler and hook.

| Field | Description |
| --- | --- |
| `id` | Job id, as assigned by the transport. |
| `job` | Name of the job. |
| `queue` | Queue it came from. |
| `strategy` | Name of the mounted strategy it came from. |
| `attempt` | Attempt number, starting at 1. |
| `attempts` | Total attempts this job may take. |
| `payload` | Validated payload, identical to the first handler argument. |
| `headers` | Transport headers received with the job. |
| `raw` | The transport-native job or message. |
| `logger` | Logger scoped to this job, or null when none is bound. |
| `updateProgress(progress)` | Reports progress, a no-op on transports that do not track it. |

## QueueError

Every failure the module reports is a `QueueError`.

```ts
try {
  await queueManager.add({ queue: 'emails', job: 'welcome', payload });
} catch (error) {
  if (error instanceof QueueError) {
    error.operation; // 'add', 'publish', 'consume', 'validate', 'timeout', ...
    error.retryable; // false when running the job again cannot help
    error.cause;     // the transport error underneath
    error.metadata;  // queue, job and other non-sensitive context
  }
}
```

`retryable` is what the manager reads when deciding whether to schedule another attempt: a validation failure or a missing handler is never retried, while a broker hiccup is.

## Job headers

Three headers travel with every job so any transport can route and retry it. They are visible in `context.headers` and can be read by other consumers of the same broker.

| Header | Description |
| --- | --- |
| `x-job` | Name of the job. |
| `x-attempt` | Attempt number, starting at 1. |
| `x-attempts` | Total attempts the publisher asked for, when it asked for more than one. |

A message that carries none of these, because it was produced outside this module, is dispatched as the job `unknown`, which an `@AnyJob()` handler picks up.
