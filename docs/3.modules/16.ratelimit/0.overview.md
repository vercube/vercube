The Rate limit module limits how many requests a client can make to a route in a window of time. Put `@RateLimit()` on a route or a controller, or set an app-wide limit in `vercube.config.ts`. Over the limit, the route answers `429 Too Many Requests` with a `Retry-After` header.

Counters live in a [Storage](/docs/modules/storage/overview) mount. In memory they count per instance. In Redis every instance shares them, so the limit holds however many replicas you run.

## Installation

::code-group
  ```bash [pnpm]
  $ pnpm add @vercube/ratelimit @vercube/storage
  ```
  ```bash [npm]
  $ npm install @vercube/ratelimit @vercube/storage
  ```
  ```bash [bun]
  $ bun install @vercube/ratelimit @vercube/storage
  ```
::

## Quick Start

::steps
### Register the plugin

`RateLimitPlugin` reads the `rateLimit` section of the config. Importing the package is what adds that section to the config type.

```ts [vercube.config.ts]
import { defineConfig } from '@vercube/core';
import { RateLimitPlugin } from '@vercube/ratelimit';

export default defineConfig({
  rateLimit: { storage: 'redis' },
  plugins: [RateLimitPlugin],
});
```

Behind a load balancer or a reverse proxy, also set `trustProxy`, see [Who a request counts against](#who-a-request-counts-against). Never set it on a server clients reach directly: they could then pick the address they are counted against.

### Mount a storage

Mount the storage the counters go to. Use Redis when more than one instance runs.

```ts [src/boot/Container.ts]
import { StorageManager } from '@vercube/storage';
import { RedisStorage } from '@vercube/storage/drivers/RedisStorage';

container.bind(StorageManager);

void container.get(StorageManager).mount({
  name: 'redis',
  storage: RedisStorage,
  initOptions: { url: process.env.REDIS_URL },
});
```

When nothing is mounted as `default`, a memory storage is mounted there with a warning, so a limit works in development without setup. A missing named mount, such as a typo in `storage: 'reddis'`, is not replaced: it fails like a storage that is down, see [Storage](#storage).

### Limit a route

```ts [src/controller/AuthController.ts]
import { Controller, Post } from '@vercube/core';
import { RateLimit } from '@vercube/ratelimit';

@Controller('/auth')
export class AuthController {
  @Post('/login')
  @RateLimit({ limit: 5, window: '1m' })
  public login(): void {}
}
```

The sixth login attempt from one address in the same minute answers:

```http
HTTP/1.1 429 Too Many Requests
RateLimit-Limit: 5
RateLimit-Remaining: 0
RateLimit-Reset: 42
Retry-After: 42
```
::

## Where a limit applies

A limit goes on a method, on a controller, or in the config. The one closest to the route wins, and exactly one limit counts each request:

- a method's `@RateLimit()` replaces the controller's
- a controller's `@RateLimit()` replaces the app-wide limit
- `@RateLimit(false)`, or `@SkipRateLimit()`, lifts every limit from a route or a controller

```ts
@Controller('/reports')
@RateLimit({ limit: 100, window: '1m' })
export class ReportsController {
  @Get('/')
  public list() {}

  @Post('/export')
  @RateLimit({ limit: 2, window: '1h' })
  public export() {}

  @Get('/health')
  @RateLimit(false)
  public health() {}
}
```

The app-wide limit is the `rateLimit` section with both `limit` and `window` set. It applies to every route that has no limit of its own, and to requests that match no route, such as a 404 or a static file.

```ts [vercube.config.ts]
export default defineConfig({
  rateLimit: { limit: 300, window: '1m' },
  plugins: [RateLimitPlugin],
});
```

The other fields of the section are defaults for `@RateLimit()`: a route that leaves `storage` out uses the config's, and so on. `priority` and `name` are the exceptions, they only apply to the app-wide limit.

### Two limits on one route

A route runs one limit, so stacking `@RateLimit()` does not combine limits. Of two decorators on the same method, the one written closest to the method wins and the other is ignored:

```ts
@Post('/login')
@RateLimit({ limit: 100, window: '1h' }) // ignored
@RateLimit({ limit: 5, window: '1m' }) // this one counts
public login() {}
```

The same goes for a controller with two `@RateLimit()`. A subclass works the same way: its own `@RateLimit()` replaces the one it inherited, and the parent controller keeps its limit.

```ts
@Controller('/public')
@RateLimit({ limit: 100, window: '1m' })
export class PublicApi {}

// 10 a minute here, still 100 on PublicApi
@Controller('/partners')
@RateLimit({ limit: 10, window: '1m' })
export class PartnersApi extends PublicApi {}
```

To enforce both a short burst limit and a long quota on the same route, count one of them yourself with `RateLimitManager.consume()`, see the [API](/docs/modules/ratelimit/api#consume).

### Which requests share a counter

| Limit on | Counter | Shared by |
| --- | --- | --- |
| a method | `Controller.method` | that route |
| a controller | `Controller` | every route of the controller |
| the config | `global` | every route without its own limit |

`Controller` is the route's own class. A controller that inherits routes and limits from a base class counts apart from the base class and from its other subclasses.

Names come from class names, so a build that minifies them can give two controllers the same name. Set `name` on the limits of a minified build.

Give limits the same `name` to share a counter between routes of different controllers:

```ts
@RateLimit({ limit: 10, window: '1m', name: 'uploads' })
```

## Who a request counts against

By default a request counts against the client address. Only the socket address is used, since any client can write an `x-forwarded-for` header. Behind a load balancer or a reverse proxy, every request comes from the proxy, so tell the module how many proxies to trust:

```ts [vercube.config.ts]
export default defineConfig({
  // one load balancer in front of the app
  rateLimit: { trustProxy: 1 },
  plugins: [RateLimitPlugin],
});
```

`x-forwarded-for` is then read from the right: each proxy appends the address it received the request from, so the entry added by your outermost trusted proxy is the client. `trustProxy: true` takes the leftmost entry, which is only safe when the proxy replaces the header instead of appending to it.

To count against something else, pass a `key` function. It runs after `@Auth()`, so it can read the user:

```ts
import { AuthProvider, recallUser } from '@vercube/auth';

@Controller('/api')
@Auth()
export class ApiController {
  @Get('/search')
  @RateLimit({
    limit: 60,
    window: '1m',
    key: ({ context }) => {
      const user = recallUser(context, AuthProvider)?.user as User | undefined;

      return user?.id;
    },
  })
  public search() {}
}
```

The function receives `{ request, ip, context }` and returns a string. `null`, `undefined` or an empty string leaves the request unlimited. `context` is null when the application turns both `requestContext` and `requestLogging` off. An API key works the same way: `key: ({ request }) => request.headers.get('x-api-key')`.

### Requests without a client address

A request without an address and without a key is **not limited**. A warning is logged once per counter:

```
A request to "AuthController.login" has no client address and was not limited.
Set rateLimit.trustProxy behind a proxy, or a key function.
```

Counting such requests together would put every client in one bucket: the first user to reach the limit would lock everyone else out. So the module lets them through and tells you.

Only the Node, Bun and Deno servers started by `app.listen()` see the socket address. Every other way of running the application needs `trustProxy` or a `key`:

| Running on | Client address | What to set |
| --- | --- | --- |
| `app.listen()`, directly exposed | The socket address | Nothing |
| `app.listen()`, behind a proxy or load balancer | The proxy's address, shared by everyone | `trustProxy` with the number of proxies |
| AWS Lambda, Azure Functions, Nitro | None, but the platform's headers come through | `trustProxy` with the number of proxies the platform puts in front. Check what its front end appends to `x-forwarded-for` (AWS API Gateway appends the client address, so `1`) |
| `app.fetch()` in your own server or in tests | None | `trustProxy`, a `key`, or `withRateLimit()` in tests |

An authenticated API can skip the address entirely and count per user or per API key with a `key` function.

## Algorithms

`fixed`, the default, counts requests in windows aligned to the clock: a one minute window resets at every full minute. It costs one storage write per request. A client can make up to twice the limit across the boundary of two windows: `limit` requests at the end of one and `limit` more at the start of the next.

`sliding` weighs the previous window by how much of it still overlaps the last `window` of time. A client that made 100 requests in the previous minute and is 15 seconds into the current one still has 75 of them counted. It smooths the boundary at the cost of one more storage read per request.

```ts
@RateLimit({ limit: 100, window: '1m', algorithm: 'sliding' })
```

`fixed` counts rejected requests too, so a client that keeps retrying stays limited until the window resets. `sliding` gives a rejected request its count back, so a client retrying over the limit still gets `limit` requests through per window.

## Storage

The counters are written with `StorageManager.increment()`. Whether two instances can lose a count depends on the driver:

| Driver | Counters | Expiry |
| --- | --- | --- |
| `MemoryStorage` | Atomic, per instance | Yes |
| `RedisStorage` | Atomic, shared by every instance | Yes |
| Nitro storages | Read and written separately, a warning is logged once | When the unstorage driver supports `ttl` |
| `S3Storage` | Read and written separately, a warning is logged once | No, counters stay forever |

Use Redis for limits that have to hold across instances. S3 is not suited to counters.

When the storage fails, `onStorageError` decides what happens:

- `'allow'` (default): the request goes through without `RateLimit-*` headers. Limits stop working, the application keeps working.
- `'deny'`: the request answers `503 Service Unavailable`. Use it where letting traffic through is worse than refusing it, such as a login form.

Either way a warning is logged at most once a minute per mount. A named mount that does not exist counts as a failing storage.

## Headers

Routes with a limit send the headers of the [IETF RateLimit header fields draft](https://datatracker.ietf.org/doc/draft-ietf-httpapi-ratelimit-headers/):

| Header | Value |
| --- | --- |
| `RateLimit-Limit` | The limit |
| `RateLimit-Remaining` | Requests left in the window |
| `RateLimit-Reset` | Seconds until the window resets |
| `Retry-After` | Same as `RateLimit-Reset`, only on a 429 |

`headers: false` leaves the `RateLimit-*` headers out. A 429 always carries `Retry-After`.

::warning
A browser can only read a 429 when it carries CORS headers. Register your CORS middleware with a priority below `-900` so it runs before the limit.
::

## Typed errors

Every route a limit applies to lists `TooManyRequestsError` (429), from `@vercube/core`, in the [generated client](/docs/modules/client/overview) and in the [OpenAPI document](/docs/modules/schema/overview). A route with `@RateLimit(false)` does not.

```ts
const res = await api.safe.post('/auth/login', { body });

if (res.error?.status === 429) {
  return showRetryIn(Number(res.response.headers.get('retry-after')));
}
```

## Order with other middlewares

The limit runs at priority `-900`, right after `@Auth()` (`-999`). An authenticated route therefore rejects a missing token before counting it, and a `key` function sees the user. To count every request, before authentication, give the limit a lower priority:

```ts
@RateLimit({ limit: 10, window: '1m', priority: -1000 })
```

## Observability

| Metric | Attributes | What it shows |
| --- | --- | --- |
| `vercube.ratelimit.limited` | `vercube.ratelimit.name` | Requests answered with 429 |
| `vercube.ratelimit.errors` | `vercube.ratelimit.name` | Requests the storage failed to count |

Metrics carry the counter name only, never the client address or key. They are recorded once [Telemetry](/docs/modules/telemetry/overview) is installed.
