A Vercube error says more than its message. It carries a `code` to look it up by, `why` it happened, and how to `fix` it:

```ansi
Error: Unresolved dependency for [Mailer] required by [SignupController]
  code: VERCUBE_DI_UNRESOLVED
  why:  Something asked the container for a key that nothing was bound to. ...
  fix:  Bind it before it is used: `app.container.bind(MyService)` in the `setup` callback of `createApp()`, ...
  link: https://vercube.dev/docs/core-features/errors#vercube_di_unresolved
```

The fields are logged with the error, so they are in your terminal in development and in the JSON line your log drain receives in production. Every code is listed [at the end of this page](#error-codes). Codes are public: they do not change between minor versions, so you can branch on them, alert on them, and search for them.

## What the client sees

The default error handler decides by environment:

| | development | production |
| --- | --- | --- |
| `HttpError` (4xx and 5xx you throw on purpose) | `code`, `why`, `fix`, `link` | `code` |
| any other error (answered as 500) | message, `code`, `why`, `fix`, `link` | nothing beyond `Internal Server Error` |

`why` and `fix` describe your application from the inside, so they stay out of production responses. `internal` context never leaves the process in any environment.

```json
{
  "status": 403,
  "name": "ForbiddenError",
  "message": "Plan limit of 3 projects reached",
  "code": "BILLING_PLAN_LIMIT"
}
```

## Describing your own errors

`defineErrorCatalog` keeps the errors of a feature in one place. Each entry becomes a function that builds the error:

```ts [src/Errors/BillingErrors.ts]
import { defineErrorCatalog, ForbiddenError } from '@vercube/core';

export const BillingErrors = defineErrorCatalog('BILLING', {
  PLAN_LIMIT: {
    message: ({ limit }: { limit: number }) => `Plan limit of ${limit} projects reached`,
    why: 'The workspace is on a plan with a fixed number of projects.',
    fix: 'Upgrade the workspace, or delete a project.',
    create: (message) => new ForbiddenError(message),
  },
});
```

```ts
throw BillingErrors.PLAN_LIMIT({ limit: 3 });
// error instanceof ForbiddenError, error.code === 'BILLING_PLAN_LIMIT'
```

Only `message` is built from values. `why` and `fix` are fixed strings, so nothing taken from a request can end up in them. Put values that help you debug in `internal`, which is logged and never sent:

```ts
throw BillingErrors.PLAN_LIMIT({ limit: 3 }, { cause: error, internal: { workspaceId } });
```

Without `create` the entry builds a plain `Error`, answered as a 500, or with the `status` you give the entry.

Set `expose: true` on an entry whose `why` and `fix` are written for the person using your API, and they are sent in production too:

```ts
COUPON_EXPIRED: {
  message: 'Coupon expired',
  why: 'The coupon was valid until its end date.',
  fix: 'Ask support for a new coupon.',
  expose: true,
  create: (message) => new ForbiddenError(message),
},
```

For a single error, `describeError` attaches the same fields to any error you already have:

```ts
import { describeError, NotFoundError } from '@vercube/core';

throw describeError(new NotFoundError('Invoice not found'), {
  code: 'BILLING_INVOICE_NOT_FOUND',
  why: 'Invoices older than seven years are deleted.',
  fix: 'Request an export from support.',
});
```

In a custom error handler, `getErrorGuidance(error)` returns `{ code, why, fix, link, expose, internal }`, or `undefined` for an error that carries none. It reads the fields by name, so it also understands an error made by evlog's `createError()`.

## Error codes

### @vercube/di

#### VERCUBE_DI_UNRESOLVED

`Unresolved dependency for [<key>] required by [<owner>]`

**Why:** Something asked the container for a key that nothing was bound to. The class was never passed to `container.bind()`, or it was bound in another container than the one that resolves it.

**Fix:** Bind it before it is used: `app.container.bind(MyService)` in the `setup` callback of `createApp()`, or `container.bind(Token, MyService)` for a symbol. Use `@InjectOptional(MyService)` when the dependency may be missing.

#### VERCUBE_DI_SYMBOL_WITHOUT_IMPLEMENTATION

`Container - provide implementation for binds with symbols.`

**Why:** `container.bind()` was called with a symbol and nothing else. A class can be its own implementation, a symbol cannot.

**Fix:** Pass the class as the second argument: `container.bind($Cache, RedisCache)`.

#### VERCUBE_DI_INVALID_FACTORY_TYPE

`Container - invalid factory type: <type>`

**Why:** A service definition in the container has a type the container does not know. Definitions are created by `bind()`, `bindInstance()`, `bindTransient()` and `bindMock()`, so this one was written into the container by hand, or by another version of `@vercube/di`.

**Fix:** Register services through the `bind*` methods only, and check with `pnpm why @vercube/di` that one version of the package is installed.

#### VERCUBE_DI_INVALID_DEFINITION_TYPE

`Container::internalDispose() - invalid def type: <type>`

**Why:** While disposing, the container found a service definition with a type it does not know. Definitions are created by `bind()`, `bindInstance()`, `bindTransient()` and `bindMock()`, so this one was written into the container by hand, or by another version of `@vercube/di`.

**Fix:** Register services through the `bind*` methods only, and check with `pnpm why @vercube/di` that one version of the package is installed.

#### VERCUBE_DI_DISPOSED

`Container - disposed, cannot create [<key>]`

**Why:** The container was disposed, by `app.close()` or `container.dispose()`, and something asked it for an instance it had not created yet.

**Fix:** Resolve what you need before closing the application. In a test, create a new application with `createApp()` or `createTestApp()` for each case instead of reusing a closed one.

#### VERCUBE_DI_DISPOSAL_REJECTED

`Container - disposal rejected`

**Why:** A promise handed to `container.trackDisposal()` rejected without a reason, so there is no original error to report.

**Fix:** Reject with an `Error` in the `@Destroy()` method or the cleanup that failed, so the cause is visible here.

#### VERCUBE_DI_INVALID_INJECT_METHOD

`IOCEngine.injectDeps() - invalid inject method <method>`

**Why:** A dependency was registered with an injection method the engine does not know. `@Inject()` and `@InjectOptional()` always register a known one, so the metadata comes from another version of `@vercube/di`.

**Fix:** Check with `pnpm why @vercube/di` that one version of the package is installed, and dedupe it (`pnpm dedupe`) when there are two.
