A Vercube error says more than its message. It carries a `code` to look it up by, `why` it happened, and how to `fix` it. This is the log line of a controller that injects a service nobody bound:

```json
{
  "level": "error",
  "error": {
    "name": "Error",
    "message": "Unresolved dependency for [Mailer] required by [SignupController]",
    "code": "VERCUBE_DI_UNRESOLVED",
    "why": "Something asked the container for a key that nothing was bound to. The class was never passed to `container.bind()`, or it was bound in another container than the one that resolves it.",
    "fix": "Bind it before it is used: `app.container.bind(MyService)` in the `setup` callback of `createApp()`, or `container.bind(Token, MyService)` for a symbol. Use `@InjectOptional(MyService)` when the dependency may be missing.",
    "link": "https://vercube.dev/docs/core-features/errors#vercube_di_unresolved"
  }
}
```

Every code is listed [at the end of this page](#error-codes). Codes are public: they do not change between minor versions, so you can branch on them, alert on them, and search for them.

## What is logged

An error that is not an `HttpError` is unexpected, so it is always logged at `error` level, with its guidance and its `internal` context.

An `HttpError` is an answer you chose to give. With request logging on (the default), its `code`, `why`, `fix`, `link` and `internal` are added to the wide event of the request, under `error`, so the request and its explanation are one line. With `requestLogging: false` it is logged by itself: at `error` level for a 5xx, at `debug` level for a 4xx.

`internal` is written to your log as it is. Do not put secrets in it, or configure redaction for `error.internal` in the [logger](/docs/modules/logger/overview).

## What the client sees

The default error handler decides by environment:

| | development | production |
| --- | --- | --- |
| `HttpError` | `code`, `why`, `fix`, `link` | `code` |
| any other error | its message, `code`, `why`, `fix`, `link` | `Internal Server Error`, nothing else |

`why` and `fix` describe your application from the inside, so they stay out of production responses unless the error is marked with `expose` (see below). `internal` is never sent to a client.

```json
{
  "status": 403,
  "name": "ForbiddenError",
  "message": "Plan limit of 3 projects reached",
  "code": "BILLING_PLAN_LIMIT"
}
```

## Describing your own errors

`defineErrorCatalog` keeps the errors of a feature in one place. Each entry becomes a function that builds the error:

```ts [src/Errors/BillingErrors.ts]
import { defineErrorCatalog, ForbiddenError } from '@vercube/core';

export const BillingErrors = defineErrorCatalog('BILLING', {
  PLAN_LIMIT: {
    message: ({ limit }: { limit: number }) => `Plan limit of ${limit} projects reached`,
    why: 'The workspace is on a plan with a fixed number of projects.',
    fix: 'Upgrade the workspace, or delete a project.',
    create: (message) => new ForbiddenError(message),
  },
});
```

```ts
throw BillingErrors.PLAN_LIMIT({ limit: 3 });
// error instanceof ForbiddenError, error.code === 'BILLING_PLAN_LIMIT'
```

Only `message` is built from values. `why` and `fix` are fixed strings, so nothing taken from a request can end up in them. Put values that help you debug in `internal`, which is logged and never sent:

```ts
throw BillingErrors.PLAN_LIMIT({ limit: 3 }, { cause: error, internal: { workspaceId } });
```

Without `create` the entry builds a plain `Error`. It is answered as a 500, or with the `status` you give the entry (400 to 599), and in production its body is still `Internal Server Error` with that status.

An error you answer with on every other request (a rejected login, a quota that is used up) does not need a stack trace, and collecting one is most of what building it costs. `stack: false` on the entry leaves it out:

```ts
QUOTA_EXCEEDED: {
  message: 'Quota exceeded',
  why: 'The key has used its requests for this hour.',
  fix: 'Wait for the next hour, or ask for a higher quota.',
  stack: false,
  create: (message) => new TooManyRequestsError(message),
},
```

Set `expose: true` on an entry whose `why` and `fix` are written for the person using your API, and `code`, `why`, `fix` and `link` are sent in production too, for an `HttpError` and for any other error:

```ts
COUPON_EXPIRED: {
  message: 'Coupon expired',
  why: 'The coupon was valid until its end date.',
  fix: 'Ask support for a new coupon.',
  expose: true,
  create: (message) => new ForbiddenError(message),
},
```

For a single error, `describeError` attaches the same fields to any error you already have:

```ts
import { describeError, NotFoundError } from '@vercube/core';

throw describeError(new NotFoundError('Invoice not found'), {
  code: 'BILLING_INVOICE_NOT_FOUND',
  why: 'Invoices older than seven years are deleted.',
  fix: 'Request an export from support.',
});
```

In a custom error handler, `getErrorGuidance(error)` returns `{ code, why, fix, link, expose, internal }`, or `undefined` for an error that carries none. It reads the fields by name, so it also understands an error made by evlog's `createError()`. `expose` is the exception: it is only reported for an error described with `describeError()` or a catalog, because other libraries use a field of the same name for something else.

### @vercube/auth

#### VERCUBE_AUTH_UNAUTHORIZED

`<message>`

**Why:** The auth provider rejected the request: its `validate()` returned an error message, or an object with an `error`. The message is the one the provider gave.

**Fix:** Send the credentials the provider expects. To change who is let in, change `validate()` of the `AuthProvider` that `@Auth()` uses.

#### VERCUBE_AUTH_PROVIDER_NOT_REGISTERED

`<source>: auth provider "<provider>" is not registered in the container`

**Why:** `@Auth()` or `@User()` asked the container for an auth provider and nothing is bound under that class. The request is refused, as a missing provider must never count as an anonymous caller.

**Fix:** Bind the provider in the `setup` callback of `createApp()`: `app.container.bind(AuthProvider, MyAuthProvider)`. A class passed as `@Auth({ provider: MyAuthProvider })` is bound as itself: `app.container.bind(MyAuthProvider)`.

#### VERCUBE_AUTH_PROVIDER_RESULT_INVALID

`AuthMiddleware: auth provider "<provider>" returned an invalid validate() result (<received>); expected null, a string, { user } or { error }`

**Why:** The `validate()` method of the auth provider returned something that says neither who the caller is nor why they are refused, such as `false`, `undefined` or a forgotten `return`. The request is refused, never let through.

**Fix:** Return `{ user }` from `validate()` when the request is authenticated and `{ error: 'reason' }` when it is not.

### @vercube/cache

#### VERCUBE_CACHE_DECORATOR_NOT_ON_METHOD

`@Cache() can only be applied to methods`

**Why:** `@Cache()` wraps a method so its result can be stored. It was put on a property whose value is not a function. The `metadata` of the error names the property and what it holds.

**Fix:** Move `@Cache()` to a method of the class. To cache a function that is not a method, wrap it with `CacheManager.cached(fn, options)`.

#### VERCUBE_CACHE_TARGET_NOT_FUNCTION

`Cached target must be a function`

**Why:** `CacheManager.cached()` was called with something that is not a function, so there is nothing to call on a cache miss. Its type is in `metadata.received`.

**Fix:** Pass the function as the first argument: `cacheManager.cached(async (id) => loadUser(id), { maxAge: 60 })`.

#### VERCUBE_CACHE_STORAGE_LIST_EMPTY

`At least one storage must be given when caching`

**Why:** The `storage` option of a cached function is an empty array. With no storage every read would miss and every write would be dropped, so the cache would be off without saying so.

**Fix:** Name at least one mounted storage in the `storage` option, for example `storage: ['memory', 'redis']`, or leave `storage` out to use the `default` mount.

#### VERCUBE_CACHE_STORAGE_NAME_HAS_COLON

`Storage name used for caching must not contain a colon`

**Why:** Every cache key starts with a base that holds the storage name, and the name is read back by splitting the key on the first colon. A name with a colon in it would resolve to another storage.

**Fix:** Rename the mount so it has no colon, in `StorageManager.mount({ name })` and in the `storage` option of `@Cache()`.

#### VERCUBE_CACHE_STORAGE_MANAGER_MISSING

`StorageManager is not registered in the container - bind it so cached entries have a storage to live in`

**Why:** Cached entries are kept in a storage of `@vercube/storage`, and the container that holds the `CacheManager` has no `StorageManager`.

**Fix:** Bind it before the first cached call: `container.bind(StorageManager)`, with `StorageManager` imported from `@vercube/storage`.

#### VERCUBE_CACHE_FALLBACK_MOUNT_FAILED

`Unable to mount a fallback cache storage`

**Why:** A cached function names a storage that nobody mounted, so the cache mounted a `MemoryStorage` under that name, and the `StorageManager` does not return it afterwards. That only happens with a `StorageManager` whose `mount()` or `getStorage()` was overridden.

**Fix:** Mount the storage yourself before the first cached call: `StorageManager.mount({ name, storage: MemoryStorage })`, with the name given in `metadata.storage`.

### @vercube/cli

#### VERCUBE_CLI_COMMAND_DECORATOR_MISSING

`[CommandRegistry] Class "<name>" is missing the @Command decorator.`

**Why:** A class was registered as a CLI command, but it carries no command metadata. The name and description of a command come from the `@Command()` decorator on its class.

**Fix:** Decorate the class: `@Command({ name: 'seed', description: 'Seed the database' })`, with `Command` imported from `@vercube/cli/toolkit`.

#### VERCUBE_CLI_ARGUMENTS_INVALID

`<problem.replaceAll>`

**Why:** `vercube init` was given a flag it does not have, or more than one positional argument. It takes one directory and refuses the rest, so a typo does not silently fall back to a default.

**Fix:** Run `vercube init --help` for the flags, and pass a single directory: `vercube init my-app`.

#### VERCUBE_CLI_DIRECTORY_NOT_EMPTY

`<dir> is not empty. Pass --force to replace its contents.`

**Why:** The directory the project would be created in already holds files. Nothing in it is replaced unless that was asked for, with `--force` or by answering the question in a terminal.

**Fix:** Pick an empty directory, or pass `--force` to `vercube init` to replace what is there. The `.git` directory is kept.

#### VERCUBE_CLI_INIT_ABORTED

`Aborted.`

**Why:** The target directory is not empty and the question whether to replace its contents was answered with no.

**Fix:** Run `vercube init` with another directory, or pass `--force` to replace the contents without being asked.

#### VERCUBE_CLI_UNKNOWN_TEMPLATE

`Unknown template "<template>". Available: <available>.`

**Why:** The value of `--template` is not one of the templates this version of the CLI ships.

**Fix:** Pass one of the templates listed in the message, for example `vercube init my-app --template api`.

#### VERCUBE_CLI_UNKNOWN_MODULE

`Unknown modules: <unknown>. Available: <available>.`

**Why:** A module that was asked for is not among the recipes that were offered. The id is misspelled, or it belongs to a newer version of the CLI.

**Fix:** Use the ids listed in the message, for example `vercube add queue` or `vercube init my-app --modules schema,testing`.

#### VERCUBE_CLI_UNKNOWN_DEPLOY_TARGET

`Unknown deploy target "<deploy>". Available: <available>.`

**Why:** The value of `--deploy` is not one of the deploy targets this version of the CLI ships.

**Fix:** Pass one of the targets listed in the message, for example `vercube init my-app --deploy node`.

#### VERCUBE_CLI_UNKNOWN_PACKAGE_MANAGER

`Unknown package manager "<packageManager>". Available: <available>.`

**Why:** The value of `--packageManager` is not a package manager the CLI can install dependencies with.

**Fix:** Pass one of the names listed in the message, for example `vercube init my-app --packageManager pnpm`.

#### VERCUBE_CLI_DENO_TEMPLATE_UNSUPPORTED

`Deno supports the api template only, got <template>.`

**Why:** The other templates are workspaces that are built with tools Deno does not run, so only the `api` template is offered for it.

**Fix:** Use `--template api` together with `--packageManager deno`, or pick another package manager for this template.

#### VERCUBE_CLI_FLAG_VALUE_INVALID

`--<flag> must be one of <options>, got <value>.`

**Why:** A flag that answers a question of a module was given a value the module does not offer. A recipe only writes the setups it was tested with.

**Fix:** Pass one of the values listed in the message, for example `vercube add queue --queue bullmq`.

#### VERCUBE_CLI_FLAG_VALUE_MISSING

`--<flag> needs a value.`

**Why:** A flag that answers a question of a module was passed without a value, or was followed by another flag.

**Fix:** Put the value after the flag, as in `--queue bullmq`, or drop the flag and pass `--yes` to take the default.

#### VERCUBE_CLI_FLAG_UNUSED

`<flags> only applies to a module that is not selected. Add the module to --modules, or drop the flag.`

**Why:** A flag that answers a question of a module was passed, but that module is not part of the project being created, so the answer would be ignored.

**Fix:** Add the module to `--modules`, as in `--modules queue --queue bullmq`, or remove the flag.

#### VERCUBE_CLI_ANSWERS_MISSING

`Missing <missing>. Pass them, or --yes for the defaults, when there is no terminal to ask in. Example: <example>`

**Why:** The command runs without a terminal, in CI or with its input piped, so it cannot ask the questions the flags left open.

**Fix:** Pass the flags named in the message, or `--yes` to take the default for each of them.

#### VERCUBE_CLI_NO_MODULES_NAMED

`Name the modules to add, such as vercube add queue. Available: <available>.`

**Why:** `vercube add` was run without a module, and it does not guess which one is meant.

**Fix:** Name one or more modules, comma separated: `vercube add queue` or `vercube add schema,testing`.

#### VERCUBE_CLI_MODULE_NAME_INVALID

`Unknown module "<name>".`

**Why:** The name is neither a built-in module nor a valid package name, so no recipe is looked up for it. A path such as `../recipe` is refused on purpose.

**Fix:** Pass the id of a built-in module, as in `vercube add queue`, or the name of an installed package that ships a recipe, as in `vercube add @acme/vercube-search`.

#### VERCUBE_CLI_PACKAGE_NOT_INSTALLED

`"<name>" is not a built-in module, and no package of that name is installed. Install it first, or pick a built-in module.`

**Why:** A name that is not a built-in module is treated as a package that ships a recipe, and no such package was found in the `node_modules` of the project.

**Fix:** Install the package and run the command again, for example `pnpm add @acme/vercube-search` and then `vercube add @acme/vercube-search`.

#### VERCUBE_CLI_PACKAGE_WITHOUT_RECIPE

`<name> does not export a recipe at <name>/recipe.`

**Why:** The package is installed, but its `package.json` has no `./recipe` entry in `exports`, which is where `vercube add` looks for a recipe.

**Fix:** Add the module by hand as the package documents it. As the author of the package, add `"./recipe"` to `exports` in its `package.json`.

#### VERCUBE_CLI_RECIPE_EXPORT_INVALID

`<name>/recipe does not export a recipe made with defineRecipe().`

**Why:** The `./recipe` entry of the package was imported, and neither its default export nor an export named `recipe` has an `apply` function.

**Fix:** As the author of the package, export the recipe as the default: `export default defineRecipe({ ... })`, with `defineRecipe` imported from `@vercube/cli/recipe`.

#### VERCUBE_CLI_VERSION_MISMATCH

`The project uses @vercube/core <core>, this CLI is <version>. Run the project's own CLI ('npx vercube add'), or upgrade every @vercube package to <version> first.`

**Why:** The project pins another version of `@vercube/core` than the CLI that is running. A recipe writes code for the version of the CLI, which may not exist in the version the project uses.

**Fix:** Run the CLI installed in the project, `npx vercube add`, or bring every `@vercube/*` package of the project to the version of this CLI first.

#### VERCUBE_CLI_ALIAS_TARGET_UNSUPPORTED

`tsconfig.json maps @/* to <target>, the recipes write their files under src/. Map @/* to ./src/*, or add the module by hand.`

**Why:** The files a recipe writes go under `src/` and import each other through `@/`. In this project `@/*` points somewhere else, so those imports would not resolve.

**Fix:** Set `"paths": { "@/*": ["./src/*"] }` under `compilerOptions` in `tsconfig.json`, or add the module by hand.

#### VERCUBE_CLI_ALIAS_MISSING

`The recipes import project files as @/..., which tsconfig.json does not map. Add "paths": { "@/*": ["./src/*"] } to its compilerOptions.`

**Why:** The files a recipe writes import each other through `@/`, and the `tsconfig.json` of the project has no `@/*` entry in `paths`, so those imports would not resolve.

**Fix:** Add `"paths": { "@/*": ["./src/*"] }` to `compilerOptions` in `tsconfig.json`.

#### VERCUBE_CLI_PACKAGE_JSON_MISSING

`No package.json in <root>. Run this in the root of a Vercube project.`

**Why:** The directory the command works in has no `package.json`, so there is no project to add anything to.

**Fix:** Run the command in the root of the project, or point at it: `vercube add queue --cwd path/to/project`.

#### VERCUBE_CLI_NOT_A_VERCUBE_PROJECT

`<file> does not depend on @vercube/core. Run this in a Vercube project.`

**Why:** The `package.json` of the application lists `@vercube/core` neither in `dependencies` nor in `devDependencies`. A recipe must not wire Vercube into a package that is something else.

**Fix:** Run the command in a Vercube project, or point at one with `--cwd`. Create a new project with `vercube init my-app`.

#### VERCUBE_CLI_PATH_OUTSIDE_APP

`<file> is outside the application.`

**Why:** A recipe tried to write a file through a path that leaves the directory of the application. A recipe only changes files inside it.

**Fix:** In the recipe, pass paths relative to the application without `..`, such as `src/services/Mailer.ts`.

#### VERCUBE_CLI_ENV_VALUE_MULTILINE

`The value of <name> spans lines, which .env cannot hold.`

**Why:** A recipe passed a value with a line break to `project.addEnv()`. In `.env` the second line would be read as another variable.

**Fix:** In the recipe, pass a single line to `project.addEnv()`. Encode a value that needs line breaks, for example as base64.

#### VERCUBE_CLI_JSON_FILE_NOT_FOUND

`<file> not found.`

**Why:** A recipe has to change a JSON file of the project, such as `package.json` or `tsconfig.json`, and the file does not exist.

**Fix:** Create the file named in the message and run the command again.

#### VERCUBE_CLI_JSON_NOT_PLAIN

`<file> is not plain JSON (comments?), edit it yourself.`

**Why:** A recipe has to change the file, and it could not be parsed as JSON. It usually holds comments or trailing commas, which rewriting the file would lose.

**Fix:** Remove the comments and trailing commas from the file named in the message and run the command again, or make the change by hand.

#### VERCUBE_CLI_SOURCE_FILE_NOT_FOUND

`<file> not found. The recipe needs it to wire the module in.`

**Why:** A recipe wires a module in by editing the files a Vercube template creates: `vercube.config.ts`, `src/boot/Container.ts` and `src/index.ts`. The one named in the message does not exist in this project.

**Fix:** Create the file named in the message at that path, or add the module by hand as its documentation describes.

#### VERCUBE_CLI_SOURCE_FILE_UNPARSABLE

`<file> could not be parsed: <reason>`

**Why:** A recipe edits the file through its syntax tree, and the file has a syntax error, so it could not be read.

**Fix:** Fix the syntax error reported in the message, then run the command again.

#### VERCUBE_CLI_CONFIG_EXPORT_UNSUPPORTED

`<file> must export its config as 'export default defineConfig({ ... })'.`

**Why:** A recipe adds its plugin to the object passed to `defineConfig()`. The default export of the config file is something else, such as a variable or the result of a function, which cannot be edited safely.

**Fix:** Write the config as `export default defineConfig({ ... })` with an object literal in `vercube.config.ts`.

#### VERCUBE_CLI_PLUGINS_NOT_ARRAY

`the 'plugins' option of <file> is not an array literal. Add <name> from <from> to it yourself.`

**Why:** A recipe registers its plugin by adding it to the `plugins` array of `vercube.config.ts`. The option is built some other way there, such as a variable or a spread, which cannot be edited safely.

**Fix:** Import the plugin named in the message and add it to `plugins` in `vercube.config.ts` by hand, or write the option as an array literal: `plugins: [QueuePlugin]`.

#### VERCUBE_CLI_CONTAINER_SETUP_NOT_FOUND

`Could not find the container setup in <file>: a function taking the container. Bind <binding> yourself with container.bind(<binding>).`

**Why:** A recipe binds its services in `src/boot/Container.ts`, inside the function that receives the container. No such function was found in that file.

**Fix:** Add what the message names to your container setup by hand, or export a setup function from `src/boot/Container.ts`: `export function useContainer(container: Container): void { ... }`.

#### VERCUBE_CLI_CREATE_APP_NOT_FOUND

`Could not find the createApp() call in <file>. Add this before it yourself: <code>`

**Why:** A recipe has to run code before the application is created, and `src/index.ts` has no top-level `createApp()` call to put it in front of.

**Fix:** Add the code from the message to the entry file yourself, before the line that calls `createApp()`.

#### VERCUBE_CLI_DEFAULT_EXPORT_CONFLICT

`<file> already has a default export. Replace it with this yourself: <code>`

**Why:** A deploy recipe has to make the handler of the platform the default export of `src/index.ts`, and the file already exports something else by default. Replacing an export the recipe did not write would lose it.

**Fix:** Replace the `export default` in `src/index.ts` with the code from the message yourself.

#### VERCUBE_CLI_IMPORT_NAME_CONFLICT

`<name> is already imported from <existing>, not <from>. Rename one of them and add it yourself.`

**Why:** A recipe has to import a name the file already imports from another module. Reusing the name would bind or register the wrong class.

**Fix:** Rename the existing import in that file, as in `import { Queue as MyQueue } from ...`, and run the command again.

#### VERCUBE_CLI_RECIPE_UNSUPPORTED

`<label> cannot be added to this project: <reason>`

**Why:** The `unsupported` check of the recipe refused this project, for example a module for a fullstack template in an API project. The reason in the message comes from the recipe.

**Fix:** Follow the reason given in the message, or leave the module out of the command.

#### VERCUBE_CLI_RECIPE_FAILED

`<label>: <reason> These files could not be restored: <unrestored>.`

**Why:** A recipe failed while it was applied. Every file the command had changed was put back, except the ones the message lists as not restored.

**Fix:** Fix what the message reports after the name of the recipe and run the command again. Restore a file listed as not restored with `git checkout -- <file>`.

#### VERCUBE_CLI_RECIPE_ID_DUPLICATE

`Two recipes share the id <ids>.`

**Why:** Two recipes in the list given to `resolveRecipes()` or `applyRecipes()` have the same `id`, so it would not be clear which one a selection means.

**Fix:** Give each recipe an `id` of its own in `defineRecipe({ id: ... })`.

#### VERCUBE_CLI_RECIPE_REQUIREMENT_MISSING

`A recipe requires "<id>", which does not exist.`

**Why:** The `requires` of a recipe names an id that is not in the list of recipes it is resolved against.

**Fix:** Correct the id in the `requires` of the recipe, or add the recipe it names to the list passed to `applyRecipes()`.

#### VERCUBE_CLI_RECIPE_CYCLE

`Recipes depend on each other in a cycle: <path>.`

**Why:** The `requires` and `after` of the recipes in the message point at each other, so there is no order to apply them in.

**Fix:** Remove one of the `requires` or `after` entries along the path shown in the message.

#### VERCUBE_CLI_DEPLOY_TARGET_CONFLICT

`Pick one deploy target, got <deploys>.`

**Why:** More than one recipe of the kind `deploy` was selected, directly or through `requires`. A project is built for one target.

**Fix:** Select a single deploy target, for example `vercube init my-app --deploy node`.

### @vercube/client

#### VERCUBE_CLIENT_MISSING_PATH_PARAMETER

`Missing path parameter "<name>" for <path>`

**Why:** The route has a `:name` or `**:name` segment in its path, and the call gave no value for it, or gave `null` or `undefined`.

**Fix:** Pass every segment of the path in `params`, for example `api.get('/users/:id', { params: { id } })`, and check that the value is defined before the call.

#### VERCUBE_CLIENT_INVALID_PATH_PARAMETER

`Path parameter "<name>" cannot be "." or ".." in <path>`

**Why:** A value in `params` is `.` or `..`, or a wildcard value has such a segment. A URL parser resolves these, so the request would reach another route than the one that was called.

**Fix:** Reject or encode the value before the call. A value taken from user input must not be `.` or `..`, and a wildcard value must not contain `./` or `../` segments.

### @vercube/devkit

#### VERCUBE_DEVKIT_ROUTES_NOT_REPORTED

`The application did not report its routes`

**Why:** The built application was run to read its routes for the `@vercube/client` route map, and its answer had no `routes` section. The `@vercube/core` the application was built with is older than this CLI and does not know that section.

**Fix:** Install the same version of every `@vercube/*` package, and check it with `pnpm why @vercube/core`. Set `build.typegen` to `false` in `vercube.config.ts` when the route map is not needed.

### @vercube/devtools

#### VERCUBE_DEVTOOLS_UNKNOWN_SECTION

`Unknown introspection section: <id>`

**Why:** The devtools API was asked for an introspection section that no provider registered. A section exists only when the package that describes it is part of the application.

**Fix:** Request one of the ids listed by `GET /_devtools/api/introspect` (under the `path` option of the devtools, `/_devtools` by default), and register the plugin of the package the missing section belongs to.

#### VERCUBE_DEVTOOLS_UNKNOWN_SIGNAL

`Unknown signal: <kind>`

**Why:** The devtools API was asked for a telemetry signal it does not keep. The path parameter of `/_devtools/api/signals/:kind` only takes the three signal names.

**Fix:** Use `traces`, `metrics` or `logs` as the `kind`, for example `GET /_devtools/api/signals/traces`.

### @vercube/di

#### VERCUBE_DI_UNRESOLVED

`Unresolved dependency for [<key>] required by [<owner>]`

**Why:** Something asked the container for a key that nothing was bound to. The class was never passed to `container.bind()`, or it was bound in another container than the one that resolves it.

**Fix:** Bind it before it is used: `app.container.bind(MyService)` in the `setup` callback of `createApp()`, or `container.bind(Token, MyService)` for a symbol. Use `@InjectOptional(MyService)` when the dependency may be missing.

#### VERCUBE_DI_SYMBOL_WITHOUT_IMPLEMENTATION

`Container - provide implementation for binds with symbols.`

**Why:** `container.bind()` was called with a symbol and nothing else. A class can be its own implementation, a symbol cannot.

### @vercube/queue

#### VERCUBE_QUEUE_MANAGER_CLOSED

`The queue manager is closed`

**Why:** `QueueManager.ping()` was called after `QueueManager.close()`, which runs when the application closes. A closed manager has no strategy left to ask.

**Fix:** Call `ping()` only while the application is running. In a test, create a new application with `createTestApp()` instead of reusing a closed one.

#### VERCUBE_QUEUE_STRATEGY_NOT_MOUNTED

`No queue strategy is mounted under "<name>"`

**Why:** `QueueManager.ping()` was asked about a strategy name that nothing is mounted under.

**Fix:** Mount it in the `strategies` option of `QueuePlugin` (`{ name, strategy, initOptions }`), or pass the `name` of a mounted strategy. A mount without a `name` is called `default`.

#### VERCUBE_QUEUE_STRATEGY_CLOSED

`The queue strategy "<name>" was closed`

**Why:** The strategy was unmounted, or the manager was closed, while `QueueManager.ping()` was waiting for it to initialize.

**Fix:** Do not call `QueueManager.unmount()` or `QueueManager.close()` while the strategy is still in use. A health check that reports this during shutdown can be ignored.

#### VERCUBE_QUEUE_STRATEGY_UNKNOWN

`No queue strategy is mounted as "<name>"`

**Why:** A job was published to, or read from, a strategy name that nothing is mounted under. The `metadata.mounted` field of the error lists the names that exist.

**Fix:** Mount the strategy in the `strategies` option of `QueuePlugin` (`{ name, strategy, initOptions }`), or correct the `strategy` option of the call or of `@Consumer()`. A mount without a `name` is called `default`.

#### VERCUBE_QUEUE_STRATEGY_INIT_FAILED

`Failed to initialize strategy "<name>"`

**Why:** The `initialize()` method of a mounted strategy threw something that is not a `QueueError`. The original error is the `cause`.

**Fix:** Read the `cause`, then correct the `initOptions` of that strategy in the `strategies` option of `QueuePlugin`, or make the broker reachable.

#### VERCUBE_QUEUE_STRATEGY_UNMOUNTED_BEFORE_RETRY

`Strategy "<strategy>" is no longer mounted`

**Why:** A job failed and was due for another attempt, but its strategy was unmounted before the retry could be published. The attempt is reported as failed so the transport keeps the job.

**Fix:** Call `QueueManager.drain()` before `QueueManager.unmount()`, so running jobs and their retries finish first.

#### VERCUBE_QUEUE_HANDLER_DUPLICATE

`Job "<job>" of queue "<queue>" already has a handler`

**Why:** Two handlers were registered for the same job of the same queue on the same strategy. The `metadata` of the error names both. A job is handed to one handler only.

**Fix:** Keep one `@Job()` method per job name in a queue, and one `@AnyJob()` method per queue. Check that the `@Consumer()` class is not bound twice.

#### VERCUBE_QUEUE_HANDLER_MISSING

`No handler registered for job "<job>"`

**Why:** A job arrived that no `@Job()` or `@AnyJob()` method handles, and `onUnhandled` is set to `fail`, so it is reported to the transport as a failed job.

**Fix:** Add a `@Job()` method for that job name to the `@Consumer()` of the queue, or an `@AnyJob()` method. Set `onUnhandled: 'ignore'` in the `QueuePlugin` options to drop such jobs instead.

#### VERCUBE_QUEUE_JOB_TIMEOUT

`Job "<job>" timed out after <timeout>ms`

**Why:** The handler ran longer than the `timeout` of the job, so the attempt counts as failed. The handler is not interrupted, it is only no longer waited for.

**Fix:** Raise `timeout` in the options of `@Job()`, or make the handler finish sooner, for example by splitting the work into several jobs.

#### VERCUBE_QUEUE_VALIDATION_PROVIDER_MISSING

`A job declares a schema but no ValidationProvider is bound in the container`

**Why:** A handler has a `schema` option, and the `QueueManager` found no `ValidationProvider` in its container to run it with. `createApp()` binds one, so the manager lives in a container that was built by hand.

**Fix:** Bind one: `container.bind(ValidationProvider, StandardSchemaValidationProvider)`, both exported by `@vercube/core`. Or remove `schema` from the options of the handler decorator (`@Job()`, `@AnyJob()` or `@Consumer()`).

#### VERCUBE_QUEUE_PAYLOAD_INVALID

`Payload of job "<job>" failed validation`

**Why:** The payload of a job did not pass the `schema` of its handler. The issues are in `metadata.issues` of the error. The job is not retried, as the same payload would fail again.

**Fix:** Publish a payload that matches the `schema` given to `@Job()`, or correct the schema when the payload is right.

#### VERCUBE_QUEUE_PAYLOAD_NOT_SERIALIZABLE

`Job payload is not serializable`

**Why:** The transport carries bytes, and `JSON.stringify()` threw on the payload. It holds a circular reference, a `BigInt`, or a `toJSON()` that throws.

**Fix:** Publish plain JSON data: objects, arrays, strings, numbers, booleans and `null`. Convert a `BigInt` to a string before `QueueManager.add()`.

#### VERCUBE_QUEUE_DELAY_UNSUPPORTED

`The "<transport>" transport cannot delay jobs`

**Why:** A job was published with a `delay`, on a strategy whose `capabilities.delay` is `false`. Waiting in this process would lose the job on a restart, so it is refused.

**Fix:** Remove `delay` from the job options, or publish through a strategy that delays jobs itself, such as `BullMQStrategy`.

#### VERCUBE_QUEUE_DELAY_INVALID

`Invalid job delay: <delay>`

**Why:** The `delay` of a job published to `MemoryStrategy` is `NaN` or `Infinity`, which is not a time the job could become due.

**Fix:** Pass `delay` as a finite number of milliseconds in the job options of `QueueManager.add()`.

#### VERCUBE_QUEUE_PUBLISH_FAILED

`Failed to publish job`

**Why:** The strategy threw something that is not a `QueueError` while `QueueManager.add()` was publishing. The original error is the `cause`.

**Fix:** Read the `cause`. For a custom strategy, throw a `QueueError` from `publish()` to say what failed.

#### VERCUBE_QUEUE_PUBLISH_MANY_FAILED

`Failed to publish jobs`

**Why:** The strategy threw something that is not a `QueueError` while `QueueManager.addMany()` was publishing. The original error is the `cause`.

### @vercube/ratelimit

#### VERCUBE_RATELIMIT_LIMIT_EXCEEDED

`Too many requests`

**Why:** The client sent more requests than the `limit` allows within the `window`. The `retry-after` header of the response says when the next one is let through.

**Fix:** Send fewer requests, or wait for the time in the `retry-after` header. To allow more, raise `limit` or shorten `window` on `@RateLimit()` or in the `rateLimit` config.

#### VERCUBE_RATELIMIT_STORAGE_UNAVAILABLE

`Rate limit storage unavailable`

**Why:** The storage that holds the counters threw while a request was counted, and `onStorageError` is `deny`, so the request is answered with 503 and not let through uncounted.

**Fix:** Make the storage mount named by the `storage` option reachable, the log of `RateLimitManager` names it. Set `onStorageError: 'allow'` to let requests through while the storage is down.

#### VERCUBE_RATELIMIT_STORAGE_NOT_MOUNTED

`Storage "<mount>" is not mounted`

**Why:** The `storage` option of a limit names a mount that the `StorageManager` does not have. Only the `default` mount is created on demand, a named one that is missing is treated as a mistake.

**Fix:** Mount it at startup: `StorageManager.mount({ name, storage: RedisStorage, initOptions })`. Or correct the `storage` option on `@RateLimit()` or in the `rateLimit` config.

#### VERCUBE_RATELIMIT_LIMIT_OR_WINDOW_MISSING

`Rate limit "<name>" needs a limit and a window, set them on @RateLimit() or in the rateLimit config`

**Why:** A `@RateLimit()` without a `limit` or a `window` takes them from the defaults, and neither the `rateLimit` config nor the options of `RateLimitPlugin` set them.

**Fix:** Give both to the decorator, `@RateLimit({ limit: 100, window: '1m' })`, or set `limit` and `window` in the `rateLimit` config or in the options of `RateLimitPlugin`.

#### VERCUBE_RATELIMIT_DURATION_INVALID

`Invalid duration <value> for "<option>", use milliseconds or a string such as '30s', '1m' or '1h'`

**Why:** An option that takes a duration got a value that is neither a positive number of milliseconds nor a number followed by a unit.

**Fix:** Pass milliseconds as a number, or a string such as `30s`, `1m` or `1h`, to the option the message names.

#### VERCUBE_RATELIMIT_LIMIT_INVALID

`<where>: limit must be a positive integer, got <value>`

**Why:** The `limit` option is the number of requests allowed per window. It is zero, negative, fractional or not a number.

**Fix:** Set `limit` to an integer of 1 or more, for example `limit: 100`, in the place the message names.

#### VERCUBE_RATELIMIT_ALGORITHM_INVALID

`<where>: algorithm must be 'fixed' or 'sliding', got <value>`

**Why:** The `algorithm` option chooses how a window is counted, and it has a value the module does not know.

**Fix:** Set `algorithm: 'fixed'` or `algorithm: 'sliding'` in the place the message names, or leave it out.

#### VERCUBE_RATELIMIT_ON_STORAGE_ERROR_INVALID

`<where>: onStorageError must be 'allow' or 'deny', got <value>`

**Why:** The `onStorageError` option says what happens to a request the storage could not count, and it has a value the module does not know.

**Fix:** Set `onStorageError: 'allow'` or `onStorageError: 'deny'` in the place the message names, or leave it out.

#### VERCUBE_RATELIMIT_KEY_NOT_FUNCTION

`<where>: key must be a function`

**Why:** The `key` option picks the client a request is counted for. It was given a value that is not a function.

**Fix:** Pass a function that returns the client key, for example `key: (ctx) => ctx.ip`, or leave `key` out to count per client address.

#### VERCUBE_RATELIMIT_NAME_EMPTY

`<where>: name must not be empty`

**Why:** The `name` option identifies the counter of a limit in the storage and in metrics. It is an empty string.

**Fix:** Give `name` a value such as `name: 'login'`, or leave it out to have the counter named after the controller and the method.

#### VERCUBE_RATELIMIT_PRIORITY_INVALID

`<where>: priority must be a number`

**Why:** The `priority` option orders the rate limit among the other middlewares. It is `NaN`, infinite or not a number.

**Fix:** Set `priority` to a finite number in the place the message names, or leave it out.

#### VERCUBE_RATELIMIT_TRUST_PROXY_INVALID

`<where>: trustProxy must be a boolean or a number of proxies, got <value>`

**Why:** The `trustProxy` option says how many proxies in front of the application may set the client address. It is neither a boolean nor a whole number of 0 or more.

**Fix:** Set `trustProxy` in the `rateLimit` config (or the options of `RateLimitPlugin`) to `true`, `false`, or the number of proxies in front of the application, for example `trustProxy: 1`.

#### VERCUBE_RATELIMIT_TESTING_NOT_SET_UP

`withRateLimit() is not set up yet: pass it to createTestApp({ extensions }) first.`

**Why:** The extension returned by `withRateLimit()` was used before an application set it up. It finds the `RateLimitManager` only once `createTestApp()` has run with it.

**Fix:** Pass the extension first: `const limits = withRateLimit(); await createTestApp({ extensions: [limits] })`, and use `limits` after that.

#### VERCUBE_RATELIMIT_TESTING_PLUGIN_ALREADY_REGISTERED

`withRateLimit(): RateLimitPlugin is already registered, set the app-wide limit on it rather than on withRateLimit().`

**Why:** `withRateLimit()` was given a `limit` and a `window` for an application that registers `RateLimitPlugin` itself. Registering the plugin a second time would replace the options the test set on it.

**Fix:** Call `withRateLimit()` without `limit` and `window`, and set them where the test registers the plugin: `app.addPlugin(RateLimitPlugin, { limit, window })`.

### @vercube/scheduler

#### VERCUBE_SCHEDULER_JOB_NAME_MISSING

#### VERCUBE_SCHEDULER_JOB_HANDLER_MISSING

**Why:** `SchedulerManager.add()` was given a job whose `handler` is not a function, so there is nothing to run.

**Fix:** Pass a function as `handler` to `SchedulerManager.add()`.

#### VERCUBE_SCHEDULER_JOB_UNKNOWN

`No job is registered as "<name>"`

**Why:** A job was asked for by a name that nothing is registered under. The `metadata.registered` field of the error lists the names that exist.

#### VERCUBE_SCHEDULER_JOB_TIMEOUT

`Job "<name>" timed out after <timeout>ms`

**Why:** The handler ran longer than the `timeout` of the job. The `signal` of its context was aborted with this error, and the run is recorded as failed.

#### VERCUBE_SCHEDULER_JOB_FAILED_WITHOUT_REASON

`Job failed`

**Why:** The handler of a job rejected with `undefined` or `null`, so there is no original error to report.

**Fix:** Throw an `Error` in the handler, so the reason shows up in the run record and in the log.

#### VERCUBE_SCHEDULER_LOCK_LOST

`Job "<name>" lost its lock`

**Why:** The lock of a running cluster job could not be extended: the store did not answer twice in a row, or another replica holds the lock now. The run is aborted so two replicas do not run the same occurrence.

**Fix:** Check that the scheduler store is reachable from this replica. Raise `lockTtl` in the job options when the handler blocks the event loop for longer than a third of it.

#### VERCUBE_SCHEDULER_SHUTTING_DOWN

`The scheduler is shutting down`

**Why:** The scheduler was stopped, and this run was still going after the `shutdownTimeout`. The `signal` of its context was aborted with this error.

**Fix:** Make the handler stop when `context.signal` aborts, or raise `shutdownTimeout` in the `SchedulerPlugin` options.

#### VERCUBE_SCHEDULER_CLOSED

`The scheduler is closed`

**Why:** `SchedulerManager.ping()` was called after `SchedulerManager.close()`, which runs when the application closes.

**Fix:** Call `ping()` only while the application is running. In a test, create a new application with `createTestApp()` instead of reusing a closed one.

#### VERCUBE_SCHEDULER_STORE_MISSING

`No scheduler store is mounted`

**Why:** An operation needed the scheduler store, to claim an occurrence or to answer a health check, and none is mounted.

**Fix:** Mount one in the `SchedulerPlugin` options: `store: { store: MemoryStore }` for a single process, `RedisStore` or `PostgresStore` for several replicas.

#### VERCUBE_SCHEDULER_STORE_INIT_FAILED

`Failed to initialize store "<store>"`

**Why:** The `initialize()` method of the mounted store threw something that is not a `SchedulerError`, usually because its backend cannot be reached. The original error is the `cause`.

**Fix:** Read the `cause`, then correct the `initOptions` of the `store` in the `SchedulerPlugin` options, or make the backend reachable.

#### VERCUBE_SCHEDULER_QUEUED_RUN_FAILED

`<message>`

**Why:** An occurrence that was handed to a queue ran in a worker and ended as failed or aborted. The message is the one of the failed run. It is thrown again so the queue counts the attempt as failed and applies its own retries.

**Fix:** Read the message and the log of the run, and correct the handler of the job named in `metadata.job`. The retries of the queue are the `attempts` and `backoff` of the `target` of the job.

#### VERCUBE_SCHEDULER_CLAIM_FAILED

`Failed to claim "<occurrenceId>"`

**Why:** The store threw while this replica was claiming an occurrence. Without a claim nobody can tell whether another replica runs it, so it does not run here and is recorded as failed.

**Fix:** Read the `cause`, and check that the scheduler store is reachable. Run the occurrence by hand with `SchedulerManager.trigger()` when it was missed.

#### VERCUBE_SCHEDULER_ENQUEUE_FAILED

`Failed to enqueue "<occurrenceId>"`

**Why:** The job has a queue `target`, and publishing the occurrence to that queue failed. The original error is the `cause`.

**Fix:** Read the `cause`. Check that the `queue` and `strategy` of the `target` name a strategy mounted in `QueuePlugin`, and that its broker is reachable.

#### VERCUBE_SCHEDULER_CLUSTER_STORE_MISSING

`Cluster jobs <jobs> need a store to decide which replica runs them. Mount one (RedisStore, PostgresStore, or MemoryStore for a single process), or set scope: 'instance' to run them on every replica.`

**Why:** A job with `scope: 'cluster'` runs on one replica per occurrence, and the replicas agree on which one through the scheduler store. No store is mounted.

**Fix:** Mount one in the `SchedulerPlugin` options, for example `store: { store: RedisStore, initOptions: { url } }`. Or set `scope: 'instance'` on the job.

#### VERCUBE_SCHEDULER_CLUSTER_STORE_LOCAL

`Cluster jobs <jobs> use the "<store>" store, which only coordinates a single process, so every replica would run them. Mount a distributed store such as RedisStore or PostgresStore, set scope: 'instance', or set allowLocalCluster: true if this really runs as a single process.`

**Why:** In production, jobs with `scope: 'cluster'` are refused on a store that lives in one process, because each replica would have its own locks and run every occurrence.

**Fix:** Mount `RedisStore` or `PostgresStore` as the `store` in the `SchedulerPlugin` options. Set `allowLocalCluster: true` there when the application runs as one process.

#### VERCUBE_SCHEDULER_CLUSTER_JOB_UNNAMED

`Cluster jobs <jobs> need an explicit name. The name is part of every lock key, and a name derived from the class can change between builds (bundlers rename colliding classes, Jobs becomes Jobs$1), so replicas of two builds would run the same occurrence. Add { name: 'billing.close-day' } to the decorator, or set scope: 'instance'.`

**Why:** A job with `scope: 'cluster'` has a name generated from its class and method. Replicas lock on the name, and a generated one is not stable across builds.

**Fix:** Add a `name` to the options of `@Cron()` or `@Every()`, for example `{ name: 'billing.close-day' }`. Or set `scope: 'instance'` on the job.

#### VERCUBE_SCHEDULER_QUEUE_TARGET_INSTANCE_SCOPE

`Jobs <jobs> target a queue with scope: 'instance', so every replica would enqueue every occurrence. A queue target needs cluster scope.`

**Why:** A job with a queue `target` also has `scope: 'instance'`. Every replica would publish the same occurrence to the queue.

**Fix:** Set `scope: 'cluster'` on the job, or remove its `target` to run it inline on every replica.

#### VERCUBE_SCHEDULER_QUEUE_MANAGER_MISSING

`Jobs <jobs> target a queue, but no QueueManager is bound. Install @vercube/queue and add QueuePlugin, or remove the job's target.`

**Why:** A job has a queue `target`, and the container has no `QueueManager`: `@vercube/queue` is not installed, or `QueuePlugin` is not registered.

**Fix:** Run `pnpm add @vercube/queue` and register the plugin with `app.addPlugin(QueuePlugin, { strategies })`. Or remove `target` from the job options.

#### VERCUBE_SCHEDULER_TARGET_INVALID

`Invalid target <target> for "<name>", expected 'inline' or { queue: 'name' }`

**Why:** The `target` of a job says where an occurrence runs. It is neither `inline` nor an object with a non-empty `queue`.

**Fix:** Set `target: 'inline'` or `target: { queue: 'reports' }` in the options of `@Cron()` or `@Every()`, or leave `target` out.

#### VERCUBE_SCHEDULER_OPTION_INVALID

`Invalid <option> <value> for "<owner>", expected one of <allowed>`

**Why:** The `scope`, `overlap` or `misfire` option of a job, or of the scheduler defaults, has a value the scheduler does not know.

**Fix:** Use one of the values the message lists. `scope` takes `instance` or `cluster`, `overlap` takes `skip` or `allow`, `misfire` takes `skip` or `run-once`.

#### VERCUBE_SCHEDULER_DURATION_INVALID

`Invalid duration <value> for "<option>", use milliseconds or a string such as '30s', '5m', '1h' or '1d'`

**Why:** An option that takes a duration got a value that is neither a number of milliseconds nor a number followed by a unit.

**Fix:** Pass milliseconds as a number, or a string such as `30s`, `5m`, `1h` or `1d`, to the option the message names.

#### VERCUBE_SCHEDULER_LOCK_TTL_TOO_SHORT

`lockTtl of "<owner>" is <lockTtl>ms, the shortest one allowed is <shortest>ms`

**Why:** The lock of a running job is extended three times within `lockTtl`. Below the minimum, a slow store round trip would let the lock expire while the job still runs.

**Fix:** Raise `lockTtl` in the job options, or in `defaults` of the `SchedulerPlugin` options, to at least the value the message names.

#### VERCUBE_SCHEDULER_RETRIES_INVALID

`retries of "<owner>" must be a whole number of 0 or more`

**Why:** The `retries` option counts the extra attempts of a failed run. It is negative, fractional or not a number.

**Fix:** Set `retries` to an integer such as `0` or `3` in the job options, or in `defaults` of the `SchedulerPlugin` options.

#### VERCUBE_SCHEDULER_TIMEZONE_UNKNOWN

**Why:** The `timezone` of a job, or of the scheduler, is a name the runtime does not know. `Intl.DateTimeFormat` rejected it.

**Fix:** Use an IANA name such as `Europe/Warsaw` or `UTC` for `timezone`, in the options of `@Cron()` or in `defaults` of the `SchedulerPlugin` options.

`Invalid cron expression "<expression>" for job "<job>": <reason>`

**Why:** The expression given to `@Cron()` could not be parsed. The end of the message is what the parser said.

#### VERCUBE_SCHEDULER_INTERVAL_TOO_SHORT

**Why:** The interval given to `@Every()` is shorter than the scheduler can keep. Occurrences are identified by their instant, to the second.

**Fix:** Pass an interval of at least the value the message names to `@Every()`, for example `@Every('1s')`.

#### VERCUBE_SCHEDULER_HTTP_SECRET_MISSING

**Why:** The `http` option of `SchedulerPlugin` mounts an endpoint that runs jobs on request. It is refused without a secret, as anyone who can reach the application could trigger jobs.

**Why:** A method of `RedisStore` was called before its `initialize()`, or after `close()`. That happens when the store is created by hand and not mounted.

**Fix:** Mount it in the `SchedulerPlugin` options: `store: { store: RedisStore, initOptions: { url } }`. The scheduler initializes the store before it uses it.

`The Postgres store is not initialized`

`No built application at <entry>. Run "vercube build" first, pass --build, or point --entry at the built entry.`

**Why:** The scheduler commands load the built application to find its jobs, and the entry file does not exist.

`ValidationProvider is not registered`

**Why:** A message arrived for a handler that has a `validationSchema`, and the websocket service has no `ValidationProvider` to check it with. The message is not handled.

**Fix:** Bind a provider in the container the websocket service is resolved from: `container.bind(ValidationProvider, StandardSchemaValidationProvider)`, both from `@vercube/core`.

#### VERCUBE_WS_MESSAGE_INVALID

`Websocket message validation error`

**Why:** The `data` of a websocket message does not match the `validationSchema` of the `@Message()` handler for its event. The peer receives an `error` frame with the issues.

**Fix:** Send `data` that matches the schema of the event. The `issues` of the `error` frame name each field that failed.
